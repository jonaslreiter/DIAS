# DIAS Agent Instructions

Repository-level guidance for AI coding agents working in this workspace. Keep it current when the pipeline, layout, naming or conventions change; when it disagrees with the code, confirm which path actually runs and fix this file.

## What This Is

DIAS means Differentiable Induction of Action Schemas. It learns lifted STRIPS action schemas from PDDL state transitions, and implements the paper [Differentiable Learning of Lifted Action Schemas for Classical Planning](https://arxiv.org/abs/2605.13282). Consult the paper when this file is not enough.

The setting, which code changes should preserve unless a task says otherwise:

- Inputs are `<s, a, s'>` triplets sampled from a **single** problem instance per domain.
- States are symbolic PDDL states over **unary and binary predicates only**, fully observed.
- Action labels are full STRIPS actions, STRIPS+ actions, or names only, depending on the experiment.
- The output is, per action schema, lifted positive and negative preconditions and lifted add and delete effects.
- Action binding is assumed injective, and the domain's predicates are known. Sampling refuses a state in which an action applies with one object in two parameters (`generate_samples._require_injective`); no domain in `pddl/` has one, and the learned domain requires distinct parameters accordingly.
- Objects are embedded by a relational GNN; slot queries plus a Sinkhorn-style rectangular assignment bind objects to schema parameters; slot activations give the learned arity.
- Auxiliary losses push toward minimal effects and restrictive preconditions, and PCGrad keeps them from overriding the prediction objective.
- Evaluation is **behavioural**: does the learned domain generate the same successor states as the real one, on held-out problems.

End to end: load a domain and one problem, sample transitions by random walk or BFS, encode them as adjacency tensors and PyG graphs, train with Lightning, read the lifted schemas off the trained parameters, score them against the original domain on the three held-out instances, and repeat per `(domain, seed)`.

## Layout

- `src/dias/` is the package. It is installed from a clone (`pip install -e .`, console script `dias`), never from PyPI, where the name is taken. `configs/`, `pddl/` and `experiments/` are **not** package data, so every documented command runs from inside the checkout. Dev tooling is the PEP 735 `[dependency-groups] dev` table (`pip install -e . --group dev`).
- `pddl/<domain>/` is one folder per domain, holding `domain.pddl`, `train.pddl`, `test-1.pddl` .. `test-3.pddl`, `strips+.yaml` (the STRIPS+ argument positions) and `config.yaml`, plus a `README.md` tabulating the instance sizes (documentation only, nothing reads it). **The folder is the manifest**: nothing lists the domains or their files, adding a domain is adding a folder, and those filenames are load-bearing (`tests/test_pipeline.py` fails on a folder missing one).
- `configs/` holds the Lightning configs `dias fit` reads, flat: the base `main.yaml`, the experiment overlays `experiment-mlp.yaml` / `experiment-noise.yaml`, the label overlays `labels-strips.yaml` / `labels-strips-plus.yaml`, and six `ablation-*.yaml`. What makes one the base and the rest overlays is the order they are passed.
- `experiments/` is what you run: the launchers (`launch.py`, `launch_threshold_validation.py`), the validation steps (`validate_runs.py`, `validate_checkpoint.py`), the collectors (`collect_results.py`, `precondition_categories.py`), their shared `pipeline.py`, `slurm/`, the orchestration configs in `configs/`, the domains the L1 baseline learned in `l1_pddl/<domain>.pddl`, the `scaling/` study, and `README.md`, the recipes users are pointed at.
- `tests/` mirrors the package: a test module is named after the module it covers, minus the package path (`tests/test_noise.py`, `tests/test_mlp_effects.py`).
- `logs/`, `local/` and `experiments/results/` are gitignored. Result tables are regenerated from `logs/`, so do not commit them; public docs must not point at `local/`.

**`experiments/pipeline.py` is the one place that resolves a path.** `EXPERIMENTS_ROOT` is its own folder and `PROJECT_ROOT` its parent; `SLURM_DIR`, `PIPELINE_CONFIGS`, `RESULTS_DIR` and `L1_PDDL_DIR` hang off the first, `CONFIGS_DIR` / `PDDL_DIR` / `LOGS_DIR` off the second, and the domain-folder layout (`domain_pddl`, `train_problem`, `validation_problems`, `domain_config`, `available_domains`, `select_domains`, `l1_domain`, and `l1_domains`) lives there too. Nothing else joins one of those paths by hand. It imports neither torch nor pymimir, so submission works on a login node.

## Code Map

- `main.py`: the LightningCLI entry point. It links datamodule metadata (`num_objects`, `relation_arities`, `num_actions`) into the model's init args; keep the two interfaces in step. `LearnedDomainCheckpoints` saves every checkpoint's learned domain beside it (see Training).
- `data/`: `datamodule.py` (`PddlGraphDataModule`, composing the rest), `datasets.py` (`PddlTransitionDataset` plus its index-list and stratified-stream views), `generate_samples.py` (BFS and random-walk exploration, `random_walk` being the one walk training and validation both sample from; sample dicts carry primitives only, never a live pymimir object), `quota.py` (`SampleQuota`, the per-action bounds), `splitting.py` (the action-stratified split), `noise.py` (`Ratio` / `ExpectedCount`).
- `models/`: `dias.py` (the LightningModule), `encoder.py` (`RelationalEncoder`), `selection.py` (`resolve_num_slots`, `SlotSelector`), `preconditions.py` (`Preconditions`, `soft_conjunction`), `effects.py` (`StaticEffects` and `StateDependentEffects` behind `EffectSource`), `prediction.py` (`SuccessorPredictor`, composing them into `A' = A + pre·Δ`), `edges.py` (`EdgeTypeLayout`, the only place that knows what an edge type id means, and the builder of the edges), `masking.py` (which `(relation, slot, slot)` cells no lifted schema can express), `objectives.py` (`DiasObjective`, returning the auxiliary terms *beside* `L_adj`, never summed into it, and `Losses.primary`, what PCGrad protects), `pcgrad.py` (`gradient_combiner` over `SingleObjective` / `WeightedSum` / `PCGrad`, taking the two scalar losses), `outputs.py` (`Channels`, `SchemaPrediction`, `SchemaLogits`), `checkpoints.py` (migration).
- `schema/`: `domain.py` (`DomainSchema`, the frozen relation/action/object metadata of one `(domain, problem)` pair, and the functions deciding what that metadata is) `action.py` (`ActionSchema` / `LiftedAtom` and their PDDL serialization), `decoding.py` (`derive_schema`, the paper's Sec. 4.5 derivation) and `export.py` (`read_learned_schemas`, a model's lifted schemas as learned, and `learned_domain`, the PDDL domain a run writes beside each checkpoint). Consumers needing only metadata use `DomainSchema` instead of building a datamodule.
- `pddl/`: `text.py` (pure PDDL string handling, imports nothing), `untype.py` (typed to untyped compilation), `transpiler.py` (`PDDLTranspiler`, binarized tensors to `ActionSchema`s), `states.py` (reading pymimir states and re-hosting one problem's state on another).
- `validation/`: `pddl.py: PddlValidator` scores any learned PDDL domain against the original, L1's as given and a DIAS run's through `dias.py: DiasValidator`, which hands it the run's learned domain; `mlp_effects.py: MlpEffectsValidator` grounds an MLP-effects run's learned preconditions and predicts the successors with its network. Plus `grounding.py` (the MLP-effects validator's worker side, torch-free), `checkpoint.py` (`load_run`, and `learned_pddl`, a run's learned domain), `successors.py` (state sampling and `score_successors`), `artifacts.py` (`PddlWorkspace`, since pymimir only parses from paths).
- `reporting/`: `labels.py`, `vega.py` (three Vega-Lite heatmap specifications), `charts.py`, `callback.py` (`SchemaChartCallback`).
- Top level: `adjacency.py` (the dense `[R, O, O]` representation and its PyG conversions), `schedules.py` (`Constant` / `Exponential` / `PiecewiseLinear`, pure functions of the global step, holding no state), `hparams.py` (round-tripping a dataclass-typed argument through hyper-parameters, which must hold primitives or `torch.load` refuses the checkpoint).

## Training

- The config chain is `dias fit --config configs/main.yaml --config pddl/<domain>/config.yaml`, plus experiment, label and ablation overlays. **`main.yaml` names no domain**, so it is not runnable alone: a domain config opens with its own `domain_path` / `problem_path`, which is what completes the chain (`tests/test_configs.py` pins that they are the folder's own files).
- **Each layer states only what it changes about the layer below, and the bottom layer is the class signature.** `DIAS` and `PddlGraphDataModule` default to the paper's full model with no noise, so `main.yaml` carries the run itself (trainer, logger, callbacks) plus what a class cannot choose: `num_slots`, the τ schedule, the four sampling bounds. A per-domain config carries only its own two paths, `aux_loss_alpha`, and, for the seven domains that sample differently, the `*_per_action_*` bounds. Do not restate a default to make it visible.
- **Every `__init__` argument of `DIAS` and `PddlGraphDataModule` carries a one-line description**, as a Google-style `Args:` block that `--model.help` / `--data.help` print. A new argument gets its line in the same commit.
- **Two arguments have no default anywhere**: `data.domain_path` and `data.problem_path`. Arguments defaulting to `None` mean "not set", not a value: `num_slots`, `precondition_tau`, `noise`, `data.seed`, and the four sampling bounds, which `SampleQuota` refuses as a group if nothing says how much to sample.
- **One seed per run.** `data.seed` defaults to `None` and `CLI._seed_the_data_from_the_run` fills it from `seed_everything`, so the saved config records the number the walk sampled under and an unseeded run stays reproducible after the fact. Launchers therefore pass `--seed_everything` alone.
- τ (`model.init_args.precondition_tau`) is the root degree of the relaxed precondition product, one of the schedule classes, configured by `class_path` / `init_args`. `Exponential` is `floor + (start - floor) * factor ** (step / every)`; rate and asymptote are independent.
- **One caveat on typed config values.** jsonargparse *merges* a configured value's fields onto the default's rather than replacing, so a schedule-typed argument must default to `None`, and switching the schedule *class* on the command line over a config that names another does not work. Keep overrides to fields.
- Ablation switches are `model.init_args` arguments defaulting to the full model, one overlay each: `use_slot_weights`, `use_precondition_loss`, `use_effect_loss`, `use_pcgrad`, `random_node_embeddings`, plus `ablation-no-aux-loss` (both auxiliary terms, α = 0).
- **The applicability term** (`model.init_args.use_applicability_loss`, off by default, not in the paper) adds to the primary loss one cross-entropy per transition asking its `precondition_satisfaction` at the bound objects (the observed arguments, or the selection) to be 1, transitions that changed nothing included, since every observed action was applicable. `L_adj` alone cannot refute a literal that only such a transition violates: where the add effects already held, failing preconditions predict it as well as holding ones, and `L_pre` then pushes the literal in (satellite's calibrate forbidding the `calibrated` it adds, take_image the `have_image`). `Losses.primary` is `L_adj` plus the term, which is what `gradient_combiner` protects; it is logged as `loss_applicability`, and `loss_adjacency`, which `best-` follows, stays `L_adj` alone. The normalizer counts it as one cell per transition. It is launched with `--set model.init_args.use_applicability_loss=true`; there is no overlay. It was on by default for a while; the per-domain `aux_loss_alpha` was retuned with it off since, and a checkpoint that does not store the switch trained without it (see Checkpoint Compatibility).
- **Observation noise** (`model.init_args.observation_noise`, 0 by default, not in the paper) scores `L_adj` as the predicted successor seen through a channel that flips each atom with that probability, `ε + (1 - 2ε)·p`. A cell the prediction confidently contradicts then costs at most `-log ε`, with a bounded gradient, so one corrupted atom of s or s' cannot outweigh the transitions that agree, while a correct prediction's loss barely moves; at 0 the loss is unchanged bit for bit. The noise overlay sets it to 0.1, which is what lets τ anneal to the exact product under noise as on clean data; the paper's noise runs softened the product with a τ floor instead. `--set model.init_args.observation_noise=ε` sets it elsewhere.
- **Equality is assumed, not learned, by default** (`data.init_args.include_equality: false`). Bindings are injective, so an equality channel would be constant at every slot pair (true where a slot meets itself, false elsewhere): it tells the model nothing. Off, `=` and a binary `eq` or `equal` a domain writes in its place (`pddl.text.is_equality_predicate`) get no channel, and the learned domain requires every schema's parameters to be distinct, as `=` under `:equality`. On, equality is a relation like any other and nothing is written for it: the learned domain spells it as the declared predicate `equal`, since PDDL forbids effects on `=`, so a learned `(not (equal ?x ?x))` or an effect on it stays in the PDDL as the failure it is and is scored. A checkpoint stores the argument with its datamodule; one without the key predates it and kept the channel, which is how `DomainSchema.from_checkpoint` and `validation.checkpoint.load_run` read it (`schema.domain.EQUALITY_BEFORE_ARGUMENT`). The eight domains with `:equality` all spell it `=`, blocks-3 and Gripper included. The paper's runs had the channel; `--set data.init_args.include_equality=true` restores it.
- **Every checkpoint has its learned domain beside it**, as `<checkpoint stem>.pddl`, binarized at `model.init_args.schema_threshold` (0.5, noise runs included; the paper's noise runs used 0.75) by `schema.export.learned_domain`. It is untyped, over the original's predicates with its types as unary predicates, because what DIAS learns about types is preconditions, negated ones included, which typed PDDL cannot write. An MLP-effects run's holds preconditions only, every active slot a parameter, with empty effects. **The two are saved and removed together by construction**, through public Lightning API: `main.LearnedDomainCheckpoints` puts the domain into the checkpoint in `on_save_checkpoint`, which every save calls, and wraps the strategy's `CheckpointIO`, whose `save_checkpoint` writes it beside the file instead of into it and whose `remove_checkpoint` deletes both. So whichever `ModelCheckpoint` saves, and at whichever hook, the domain is the checkpoint's own; a weights-only save skips callback hooks and gets none.
- The MLP-effects model is `model.init_args.state_dependent_effects: true` (`configs/experiment-mlp.yaml`). Its effect MLP has SiLU activations between the linear layers and its output goes through the same arity mask as the static tensor; both are load-bearing, so **a checkpoint whose effect MLP predates them is refused on load** rather than migrated.
- Noise ablations set `data.init_args.noise` to one of the two dataclasses; unset means clean transitions. **`configs/experiment-noise.yaml` changes two things beside the noise, identically for every domain: `observation_noise: 0.1` and `batch_size: 50`.** The τ schedule (floor 0), `schema_threshold` (0.5) and the sampling bounds stay those of the clean setup. The paper's noise runs had no observation noise and adjusted four things: per-action minima raised to 200/100, batch 50 as here, a τ floor of 0.1 and a threshold of 0.75 (`model.init_args.observation_noise=0`, `model.init_args.precondition_tau.init_args.floor=0.1`, `model.init_args.schema_threshold=0.75`, `data.init_args.min_per_action_{train,valid}_floor=200/100`). The trade between the two: the τ floor softens the whole precondition product, which keeps true preconditions that noise violates often (blocks-3, hanoi) but also hides the unsatisfiable literals of spare slots, so actions go dead elsewhere and decoding needs 0.75; with the floor at 0 and `observation_noise`, a precondition noise violates in more than a few percent of an action's transitions is dropped (blocks-3, hanoi, driverlog), while dead literals are punished and most other domains learn better than the paper's setup from 2 flips up. `min_per_action_*_floor` only ever **raises** the per-domain minimum, which is why such an override states a floor rather than a value: overlays and overrides compose *after* the domain config. **`ExpectedCount` noises static relations too by default**, as the paper's runs did (`fluents_only: false`); `fluents_only: true` spends the whole budget on the fluents, 2 to 25 times their noise at the same budget, and is not what the paper measured. Its budgets are per state and both states of a transition are corrupted, so 1, 2, 4 and 8 flips per transition are budgets of 0.25, 0.5, 1 and 2.
- The default batching strategy is `stratified`, an effectively unbounded iterable dataset, so run length comes from `trainer.max_steps`, not dataset exhaustion.
- The default logger is W&B (`project: dias`, `entity: null`, meaning the logged-in account or `$WANDB_ENTITY`). No account appears anywhere in the code. Checkpoints are written under `logs/dias/<run_id>/checkpoints/` as `final-epoch*.ckpt` and `best-epoch*.ckpt`.
- **The last encoder convolution has no bias**, deliberately: nothing is normalised after it, so it reaches the assignment as a per-slot constant that Sinkhorn's row scaling removes exactly, and no gradient above float32 round-off ever reached it.
- **What reproducibility is promised.** A run repeats exactly from `(domain, seed)`: `configs/main.yaml` sets Lightning's `trainer.deterministic` (do not add a second flag), which raises on any operation without a deterministic implementation. On CPU the thread count decides the trajectory with or without it, which is why `tests/test_training_characterization.py` sets `torch.set_num_threads(1)` and compares at `TRAJECTORY_TOLERANCE` (1e-4) while the forward golden keeps 1e-6.

## Validation

- Validation is behavioural, never string-based, and every validator scores a learned PDDL domain: its actions are merged into the original domain as separate actions (or, for MLP effects, grounded on their own), and the successor sets compared on `test-1..3.pddl`. Which problems those are is the folder layout; `experiments/configs/validation.yaml` holds only the sampling knobs, the seeds and `force_injective`.
- **A trained model's schema is read through `DIAS.schema_logits()` and nowhere else.** It returns the effect and precondition logits with the arity mask already applied, plus the slot-weight logits as the forward pass applies them (`SlotSelector.applied_slot_weight_logits`: infinite for a slot always used at full weight, which is every slot under `use_slot_weights: false` and every slot within the arity under `per_action_slots`). Reading `model.predictor.*` directly is wrong: the raw parameters hold untouched noise at cells no lifted schema can express, and a model that does not learn its slot weights leaves their logits at the zero initialisation, which decodes every slot inactive. `schema_logits().effects` is `None` for a state-dependent model, which is how readers learn there are no lifted effects.
- **A checkpoint becomes PDDL through `schema.export`**: `read_learned_schemas` binarizes at a threshold and transpiles, as learned, and `learned_domain` adds the header and, for a run that did not learn equality, the distinctness. `validation.checkpoint.learned_pddl` is how a validator gets a run's: the domain written beside the checkpoint, or extracted anew when a threshold is given or none was written (a run from before the files existed). `experiments/precondition_categories.py` counts what `read_learned_schemas` returns, since written distinctness is not learned.
- **`force_injective` (off everywhere: `validation.yaml`, the validators, `validate_checkpoint.py --force-injective`) replaces whatever a learned domain says about equality with distinctness of every two parameters** (`pddl.text.force_distinct_parameters`): every equality literal, learned or written, in preconditions and effects is dropped first. A run that did not learn equality already writes exactly that, so the flag changes nothing there; it is how a run that learned equality, or L1, is scored as binding injectively. No domain in `pddl/` has an applicable grounding that repeats an object, so it removes no successor a correct schema has. Result JSONs record `force_injective`, and `--resume` refuses results scored the other way or before the key existed.
- A caller that already knows the slot binding asks `DIAS.apply_schema(adjacency, selection, y_action)`, which deliberately does **not** re-check the preconditions: applicability was already decided by grounding. `DIAS.retarget(num_objects)` is how an instance size changes.
- Reading a schema off a checkpoint binarizes slot activations, effects and preconditions at one threshold. It applies uniformly: lowering it activates more slots *and* adds effects and preconditions. A run's own is `schema_threshold`; `--threshold` (`validate_runs.py`, `validate_checkpoint.py`) or `launch.py --validation-threshold` extracts the domain anew at another, for DIAS and MLP-effects runs alike, and is refused for L1. The result JSON records the threshold scored at.
- **Precision and recall are micro-averaged over per-action counts.** Every validator returns the same payload: `action_stats` plus the `tp`/`fp`/`fn` they sum to, and `collect_results` sums those across a seed's problems. `score_successors` is the one scorer, and it reports one measure, attributed to actions: a successor reached under the wrong operator is a false positive there and a false negative under the right one. There is deliberately no second union-over-actions count beside it; the state-level question survives as `matches` / `accuracy`. Soundness is precision, completeness is recall.
- **Validation states come from training's own random walk, run on the held-out problem**, unless `validation.yaml`'s `sampling` block says `strategy: bfs`. The block is one of the dataclasses in `successors.SAMPLINGS`, read by `sampling_from_record` (keys left out take the dataclass defaults) and handed to every validator's `setup` as one `Sampling`. `WalkSampling` (`sample_walk_states` over `generate_samples.random_walk`) draws `num_samples` (500) per problem from walks of `walk_length` (2,000) steps from the initial state: at least `min_walks` (5) of them, and more until every action schema is applicable in at least `num_samples` over the number of schemas of the distinct states visited, as training's walk runs until each action name has its quota (`MAX_WALKS` bounds it). Each schema then gets that share of the sample, drawn uniformly from the visited states where it applies, so every schema's recall is scored. Independent walks rather than one long one, because nothing tells a stuck walk from a live one: a Sokoban box in a corner leaves the player's moves applicable. `BfsSampling` is the paper's draw, kept to reproduce it: 250 of the first 500 states a breadth-first search reaches, which on test-2 and test-3 lie within a few actions of the initial state and never make satellite's take_image applicable, nor spanner's tighten_nut. Results record `Sampling.record()` as `sampling`, and `--resume` refuses results sampled otherwise; a JSON without the key was drawn by `BfsSampling()` (`UNRECORDED_SAMPLING`, whose settings the config never changed). The MLP-effects progress header carries the record too.
- **The sampled states are drawn freshly but always recorded.** `sample_seed` is null in the config, `successors.resolve_sample_seed` draws one per run, every validator stores it and the result JSON carries it, so passing it back reproduces exactly those states. The generator is the validator's own, never the global `random`.
- The MLP-effects validator is the only one with parallelism, because its per-state work is grounding plus a batched forward pass; DIAS and L1 validate 500 states in seconds. `Validator.grounds_in_parallel` marks it, and `validate_runs.py` defaults its `num_workers` to `pipeline.allocated_cpus()`. **Its cost follows how permissive the learned preconditions are**, and a bad schema grounds tens of millions of actions per driverlog test-3 state. `validation/grounding.py`, which imports no torch, grounds one state per task in workers that exit after `states_per_worker` states, since pymimir keeps every ground action until its process exits (over 20 GB per worker there). **The model runs on the `K x K` grid of a grounding's bound objects**, which is `apply_schema` on the whole instance because the projected effect is zero elsewhere; a slot repeating an earlier slot's object shares its row and column. A successor is the XOR of a random 128-bit key per cell it flips, with the same keys on the ground-truth side.
- **Validation reads a run's final checkpoint by default**, not its best one: `best-` follows `valid/loss_adjacency`, the relaxed adjacency loss at the current τ, which decays over training, so an early value is not comparable with a late one, and it leaves out the auxiliary terms. On the paper-setup runs it picked step 900 of 10000 for one sokoban run, whose schema recalls 0.705 of the successors against the final one's 0.971. The paper's numbers were scored on `best-`, which `--checkpoint best` (`validate_runs.py`, `validate_checkpoint.py`, `launch_threshold_validation.py`, `precondition_categories.py`) and `launch.py --validation-checkpoint best` select. `validation.checkpoint.resolve_checkpoint` picks the newest file of the name by mtime, because a re-run seed reuses the run id and Lightning writes a `-v1` file beside the old one. Every validator reaches it through `load_run`.
- Sweep validation writes `logs/validation/<experiment>/<domain>/seed<seed>.json` after every problem, with the learned domain it scored beside it as `seed<seed>.pddl`, and mirrors numeric metrics to the resumed W&B run (none for L1, which has no run). **Its `status` is `ok` only when every held-out problem scored** (`partial` or `validation_failed` otherwise), and `collect_local` reads nothing else. `--resume` keeps the problems an earlier run on the same checkpoint scored and draws the rest with its sample seed. Every validator also appends each state's score to `seed<seed>.<problem>.states.jsonl` as it finishes and skips those states when resumed, `combine_scores` summing them as `score_successors` would, so a validation longer than any time limit still finishes over several runs. The file's header names what the scores depend on (the MLP-effects validator's checkpoint, `PddlValidator.scored_digest` for a learned domain, plus problem, sample seed and sampling), and a file with another header is started over.
- **Validation spells equality one way: the predicate `equal`.** Both domains go through `pddl.text.equality_as_predicate`, which rewrites `=` and a binary `eq` or `equal` (L1 writes whichever its input domain had) as `equal`, and the problem through `pddl.untype.with_equality_facts`, which asserts `(equal o o)` for every object in place of the equality facts it had, refusing one between two objects. Nothing converts back. The original domain is sampled in that form too, so its states carry the `equal` facts, which a learned effect on `equal` then changes like any other atom. In the MLP-effects grounding domain `equal` stays static, since its states are rebuilt from the original domain's atoms, which spell it `=`.
- **`PddlValidator` reads types however a learned domain spells them**: a learned parameter type the original declares neither as a type nor as a unary predicate is refused, since no problem would assert it and the schema would silently apply nowhere. The files in `experiments/l1_pddl/` are L1's output with equality written as `=` and the types as in `domain.pddl`; `tests/test_pddl.py` scores each against its domain.
- `validate_checkpoint.py --validator {dias,mlp,l1}` is the single-model, single-problem entry point; `l1` takes any learned PDDL domain as `--learned-domain`.

## Sweeps

- `experiments/launch.py` is the authoritative launcher, structured as `parse_args -> build_plan -> describe -> execute`; `LaunchPlan` is where every rejection happens, so nothing reaches sbatch unless the whole grid is valid. Per domain it submits a training array plus a `--dependency=aftercorr` validation array, or runs the same steps sequentially with `--backend local`.
- One run is one `(domain, seed)`; the array task id **is** the seed, so `--seeds 3 7-9` becomes a sparse array spec and the dependency still pairs each seed's two tasks. Run ids are `<experiment>-<domain>-s<seed>` (`validate_runs.run_id_for`), which is how the validation array finds the checkpoint with no id handoff. Re-running a seed under the same `--experiment` overwrites its result JSON.
- `--experiment-type {dias,mlp,noise,l1}` picks the overlay and the validator; `--labels strips|strips-plus` composes `labels-strips.yaml` / `labels-strips-plus.yaml` after it (action names, the default, need none), and `--ablation` one `ablation-*.yaml` on top (orthogonal, always the DIAS validator). `l1` trains nothing: it validates `experiments/l1_pddl/<domain>.pddl` once per domain (seed 0, which only draws the states, unless `--seeds` or `--num-runs`), over every domain L1 learned (`pipeline.l1_domains`, all but satellite-recal) unless `--domains` names some, and refuses a domain it did not learn as well as `--labels`, `--ablation`, `--sweep`, `--set` and `--validation-threshold`.
- `--validate-only` submits the validation array alone, with no dependency, and writes the same `logs/validation/<experiment>/` JSONs. **Neither checkpoint name marks a finished run**: `final-` is unmonitored and `best-` follows `valid/loss_adjacency`, so both are rewritten throughout training. `launch.finished_training` compares the `final-` step against the `max_steps` in the run's own saved `config.yaml`, and `build_plan` refuses anything short of it unless `--allow-unfinished`.
- `--sweep AXIS` submits the whole grid once per value into `<experiment>-<tag><value>`. Axes live in `launch.SWEEP_AXES`: `aux-loss-alpha` (tag `aux`), `num-slots` (`slots`), `tau` (`tau`, overriding the schedule's `every` field), `dataset-size` (`n`), `noise` (`f`: flips per transition, a quarter each added and removed per state, with `--experiment-type noise`). An axis value sets its parameter times `SweepAxis.scale`. Each sub-experiment is an ordinary experiment downstream; nothing in `validate_runs.py` or the Slurm scripts knows about sweeps. A sweep is rejected together with `--set` on any of its parameters, and `aux-loss-alpha` additionally with `--ablation no-aux-loss`.
- `dataset-size` is the one axis moving several parameters at once: it pins min and max train to N, min and max valid to N/2, and both floors to the same, which also neutralises any per-action floors a run sets (the paper's noise setup raised them to 200/100). No column reproduces a domain's default run.
- Sweep and `--set` overrides are appended last on the Lightning command line, so they beat the per-domain config.
- `collect_results.py` aggregates into the paper's `P / R / N_S / N_C / N_SC` table, P and R to two decimals and never rounded up to 1.00. `--sweep AXIS` or `--threshold-sweep` gives domain × value matrices (`--markdown`: one table, a row per domain and value, the domain's configured value in bold), rebuilding the sub-experiment names by importing `launch.sweep_experiment_name` and `launch_threshold_validation.threshold_experiment_name` rather than re-deriving them; keep it that way. Without a sweep, `--experiment` takes several unrelated names and `--markdown` writes one document with a cross-experiment summary plus one table per experiment.
- `precondition_categories.py` is the other collector: it reads no result JSON, but reopens each `(domain, seed)` checkpoint and sorts every precondition atom, learned and ground truth, into equalities, unary and binary static literals, and positive and negative fluent literals. Ground truth is parsed off `pddl/<domain>/domain.pddl`, and a static predicate is one occurring in no action's effect, which is also what pymimir reports.
- `launch_threshold_validation.py` re-runs only the validation step of a finished DIAS, noise or MLP-effects experiment at several thresholds (default `0.1, 0.25, 0.5, 0.75, 0.9`), into sibling `logs/validation/<experiment>-thr<T>/` directories, never writing to the source. 0.5 is re-run rather than reused so every column comes from one code path. W&B is forced off there, since mirroring works by resuming the training run and a second threshold would overwrite the first's summary.
- `--no-wandb` covers both steps on both backends, training logger included; without a logger the run directory comes from `trainer.default_root_dir`, so `launch.run_directory_args` (mirrored in `experiments/slurm/train.sh`) names `<logs>/dias/<run_id>` explicitly.

## Slurm

- Per-domain resources are `experiments/configs/slurm-resources.yaml` (training), `slurm-resources-validation.yaml` (validation) and `slurm-resources-validation-mlp.yaml` (the MLP-effects validator's, whose cost follows how permissive the learned preconditions are), same schema (`defaults` plus per-domain overrides), resolved independently. `pipeline.validation_resources_file` picks the validation file by validator for `launch.py` and `launch_threshold_validation.py`, and `--slurm-resources-validation` overrides it. Treat them as the source of truth rather than hardcoding a partition or GPU size anywhere. Training takes GPU shards with no partition pinning; validation is CPU-only.
- The scripts under `experiments/slurm/` open with a `── site configuration ──` block holding every line specific to one cluster, including `DIAS_ENV_SETUP`. Nothing below the end marker is site-specific, and the scripts defer all experiment semantics to the Python and YAML.
- Nothing in the Slurm path assumes the submission directory: Slurm runs a spool copy, so launchers pass absolute script and `--output` paths and export `DIAS_ROOT`.
- `train.sh` and the scaling benchmark export `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, because co-tenants on a shared GPU see the *reserved* pool and that setting is what makes the per-domain shard reservations hold.
- **`train.sh` caps PyTorch's allocator at the job's share of the card**, appending `per_process_memory_fraction` to `PYTORCH_CUDA_ALLOC_CONF`: `SLURM_SHARDS_ON_NODE` over the shards per GPU read off the node's `Gres` (24 on the 24 GB partition, 48 on the 48 GB one; `DIAS_SHARDS_PER_GPU` overrides). A run outgrowing its shards therefore dies with an out-of-memory error rather than taking a co-tenant's memory; raise its `gres` in `slurm-resources.yaml`. A whole-GPU job gets no cap.
- No script requests a QoS; the jobs run under the account's default.
- **Every Slurm script sources `experiments/slurm/memory_guard.sh`**, which ends the job once its RAM and swap together exceed its allocation. This cluster's Slurm caps RAM at `--mem` but leaves swap unconstrained (`ConstrainSwapSpace=no`) and its nodes swap to zram, so a job past its allocation was swapped out without bound: noisy validations whose learned domains ground without bound took nodes down that way. A job cannot write its cgroup's limits (they are root's), so the guard reads them every five seconds, `memory.memsw.usage_in_bytes` against `memory.limit_in_bytes` of the job's cgroup under v1 or `memory.current` plus `memory.swap.current` against `memory.max` under v2, and kills the batch script when over, after which Slurm ends the rest of the job. A job it ends needs a larger `mem` in its resources file; do not relax the guard. It is off where there is no readable Slurm memory cgroup, and never fires where Slurm constrains swap itself.

## Reporting and Logging

- **The library configures no logging.** Every module reports through `logging.getLogger(__name__)` and only an entry point installs a handler (`dias.main.main`, `pipeline.configure_logging`), which is what keeps `dias` importable inside another application and why `src/` contains no `print`. Scripts take `-v` / `-q`, and `DIAS_LOG_LEVEL` overrides both, which is how a Slurm job with a fixed command line is made verbose.
- **INFO is for state changes someone waits on, once each; anything per-step or per-batch is DEBUG.** Messages carry values as `%s` arguments, never f-strings, so a suppressed line costs nothing.
- `pipeline.run_command(..., capture=True)` for sbatch, which needs the job id; `capture=False` for a local training run, which needs to inherit the terminal.
- The learned schema is reported by `SchemaChartCallback`, registered in `configs/main.yaml`, not by the model. Six panels go out as `wandb.Table`s bound to the Vega-Lite specifications in `reporting/vega.py`, every `log_every_n_validations` validation epochs and once at `on_fit_end`. The selection panel re-runs the forward pass inside `torch.random.fork_rng`, because a diagnostic must not shift the run's random stream. Without a W&B logger it logs nothing.
- **Four details of the W&B panel are not in the SDK's surface and would break silently if renamed upstream**: the query is rewritten to `historyTable` with its `extraKeys` and `index` arguments (without `index` the panel comes up empty), the panel sets `showStepSelector` (without it there is no slider), `index` is fixed at the *first* logged step so the configuration stops moving (W&B rewrites it on every log, and pointing at a still-uploading table made panels blink), and a colour bar is suppressed with `"legend": false`, not the `null` the schema specifies. The specifications live in the run's own entity, and `charts.register` must use `updateCustomChart` as well as `create`, since `create_custom_chart` cannot update.

## Naming

**Code names follow the paper's, and a new name is chosen by looking the concept up there first.** A name disagreeing with this table is a bug in the name.

| Paper | Code |
| --- | --- |
| relations / predicates `p`, arity `\|p\|` | `relation_names`, `relation_arities` |
| action schema `a`, arity `\|a\|` | `action_names`, `action_arities` |
| keys `K` | the encoder's `node_embeddings` |
| queries `Q^a` | `SlotSelector.slot_queries` |
| correspondence matrix `C^a` | `correspondence` |
| soft assignment `S^a`, selection `S̃^a` | `selection` |
| slot probabilities `w^a` | `slot_weight_logits`, `slot_weights` |
| number of slots `M`, objects `O`, embedding width `d` | `num_slots`, `num_objects`, `object_dim` |
| lifted atom `p(x1, ..., x\|p\|)` | `schema.action.LiftedAtom`, over `slots` |
| `P_add` / `P_del` / `P_pre+` / `P_pre-` | `Channels.positive` / `.negative` on `effects` / `preconditions` |
| `p_pre` | `precondition_satisfaction` |
| τ, the root degree of the relaxed product | `precondition_tau` (the schedule), `tau` (the value at a step) |
| `L_adj`, `L_aux`, weight `α` | `Losses.adjacency`, `Losses.auxiliary`, `aux_loss_alpha` (`alpha` where the quantity stands alone) |
| PCGrad's norm cap (App. A.2.2) | `pcgrad_norm_cap` |
| `N_min^tr` .. `N_max^val`, per action name | `min_per_action_train` .. `max_per_action_valid` |
| derivation of action schemas (Sec. 4.5) | `schema.decoding.derive_schema` |
| soundness / completeness | `precision` / `recall`, `tp` / `fp` / `fn` |

Three deliberate departures. **A relation is a predicate that became a channel of the adjacency tensor**, which `schema.domain.tensor_relations` decides, so `pddl/` and `transpiler.py` say `predicate_*` for the PDDL declaration and everything tensor-side says `relation_*`. **An argument named for a tensor axis keeps the axis's name** (`y_action`, `edge_index`), which is PyG's convention. And **the MLP-effects model is not a baseline**: it is one configuration of the same model, so it is "MLP effects" throughout, and the word baseline is left to L1, which is another system's output.

**An attribute of a PyG `Data` object must not have `index` or `batch` anywhere in its name unless it means what PyG takes those to mean.** `Data.__cat_dim__` and `Data.__inc__` key on the substring: a key containing `index` is concatenated along the last axis and offset by `num_nodes` per graph. That is why the action label on a graph is `y_action`; named `action_index`, three transitions labelled 0, 1, 2 over a 4-object instance batch to `[0, 5, 10]`, silently. The restriction is on `Data` attributes alone, so `PddlTransitionDataset.action_indices` keeps the clearer name.

## Checkpoint Compatibility

- `models/checkpoints.py` migrates old checkpoints. **There are three formats and one rule from each to the next**: an absent stamp (`UNVERSIONED`), the layout the paper's runs were written with, version 1, and `CHECKPOINT_VERSION = 2`. `_from_unversioned` brings the first to version 1; `_from_version_1` brings version 1 to 2, which turned the applicability term on by default, so a checkpoint that does not store `use_applicability_loss` reads as trained without it. The default is off again, which needed no rule, since every version 2 checkpoint stores the switch. Checkpoints of the branches that led to version 2 may also store `precondition_loss` and `rejection_samples`, of a reject form of `L_pre` that was removed again; loading drops them as it drops any argument the constructor does not take, and neither changes what the trained model computes. `migrate` applies every rule a checkpoint is behind, and a stamp higher than the current one is refused. **A further change to what the model stores, or to a default an older checkpoint relies on, needs version 3 and a rule of its own**, because editing an earlier rule would change what an already-published checkpoint means.
- **Migration is driven by the stamp, not by a failed load**, because Lightning silently drops a hyper-parameter it does not recognise instead of raising.
- For the same reason, **renaming a constructor argument of `DIAS` needs an entry in `_RENAMED_HPARAMS` and a line in `tests/test_checkpoint_layout.UNVERSIONED_HPARAM_NAMES`**. A datamodule argument does not, since nothing feeds stored datamodule hyper-parameters back to a constructor.
- If checkpoint naming, run directory layout or logger config changes, update the validation loaders and sweep scripts in the same change.
- **A run's relations are rebuilt in the order it was trained on** (`DomainSchema.from_run`, which `load_run` calls with the model's stored `relation_arities`), and a domain file that no longer gives that order is refused, never read with its channels shuffled. Relations sort by name, and until 2026-10-13 blocks-3 and Gripper spelt equality as their own `eq`, which sorts elsewhere than `=`: blocks-3's held of every object, so its earlier runs read `=` where `eq` sorted (`EQUALITY_SPELT_BEFORE_ARGUMENT`); Gripper's held of the rooms only, which `=` does not express, so its earlier runs are refused and are scored with main's code and domain files.

## Editing Rules

- Prefer minimal, behavior-preserving changes, and preserve the distinction between single-domain training, per-checkpoint validation and sweep orchestration.
- Do not silently change experiment semantics stored in YAML or config defaults without updating the runners and the docs in the same task; the same goes for path conventions.
- Treat the `pddl/<domain>/` folder as the source of truth for per-domain paths, reached through `experiments/pipeline.py`, and `pddl/<domain>/config.yaml` for per-domain overrides.
- The test suite must run on the oldest supported Python (3.10), so `unittest.TestCase.enterContext` is out; use `tests/support.temp_dir(self)`. CI runs 3.10 to 3.13 across three jobs: `format`, `test`, and `install`, which does a non-editable install into an empty venv and imports the package from another directory, so a missing module or an unavailable wheel fails there rather than on a user's first clone. Dropping a Python version means dropping it from the matrix, `requires-python` and the README together.
- isort's `src_paths` lists `experiments` **and** `experiments/scaling`, because the scaling scripts import each other as siblings; without the nested entry the `format` job fails.

## Documentation Rules

- The public docs are `README.md` (what DIAS is, install, quickstart, domains, a short reproduction section), `experiments/README.md` (the full recipes) and `experiments/scaling/README.md`. They must not point at `local/`, nor at anything under `logs/` or `experiments/results/`, which no clone has.
- **The README's BibTeX block is the only citation in the repository, and there is no `CITATION.cff`.** GitHub's cite button does not serve a stored entry: it renders one through ruby-cff, which derives the key from the first author's family name, the first three title words and the year, and emits a field set fixed per entry type that nothing maps to `eprint`, `archivePrefix` or `primaryClass`. A `CITATION.cff` could therefore only state a second, differently encoded version of the same paper, which is why it was removed rather than kept in step.
- **A config does not describe its own parameters.** Every argument a Lightning config sets is documented in its class signature and printed by `--model.help` / `--data.help`, so a comment restating what a value does is a second place to keep in step. What a comment there is for is what the signature cannot say: why *this* file sets *this* value, and how it composes with the others. `experiments/configs/*.yaml` are not Lightning configs, so they document their own schema, but by pointing at the code that reads it.
- Keep terminology precise and aligned with the paper: predicates, lifted action schemas, preconditions, add and delete effects, successor states, STRIPS, STRIPS+.
- **Prose is not hard-wrapped, and it has no dashes.** One paragraph is one line, in markdown, docstrings and `#` comments alike; an example command is one line however long, and so is a long string literal. Line structure is reserved for things that have one anyway: list items, tables, code blocks, and the real multi-line commands in `experiments/slurm/*.sh`. Where a dash would have gone, use a colon, a semicolon, a comma or parentheses. This is about the punctuation, not the character: `--` is the same device and no more welcome.

## Instance-Size Scaling Study

`experiments/scaling/` is a self-contained one-off analysis of iterations per second and peak GPU memory as the *instance* grows. It produces timings, not schemas, and is intentionally not wired into `launch.py`. It measures the ordinary training path by instantiating `dias.main.CLI(run=False)` on the real config chain and attaching a timing callback, so nothing is stubbed. Its instances are committed, so running it needs neither the upstream generators nor their toolchain. Details are in `experiments/scaling/README.md`.
