# DIAS Agent Instructions

This file is the permanent repository-level guidance for AI coding agents (GitHub Copilot, Claude Code, and others) working in this workspace. Keep it up to date when the codebase, pipeline, naming, or experiment conventions change.

## Purpose

DIAS means Differentiable Induction of Action Schemas. The repository implements the training, validation, and experiment pipeline for learning lifted STRIPS-like action schemas from PDDL state transitions, matching the paper "Differentiable Learning of Lifted Action Schemas for Classical Planning".

The core problem setting is:

- Inputs are state-transition triplets `<s, a, s'>` sampled from a single planning problem.
- States are symbolic PDDL states represented through unary and binary predicates.
- Depending on the experiment, action labels may be full STRIPS actions, STRIPS+ actions, or action names only.
- The goal is to learn lifted preconditions and lifted add/delete effects for each action schema.

## Repository Truths

- The installable package is `dias`, defined via `pyproject.toml` with console entry point `dias = dias.main:main`. **It is installed from a clone (`pip install -e .`), never from PyPI**: the name is taken there by an unrelated project, so `pyproject.toml` carries only what pip itself uses and no index-only metadata (no classifiers, keywords or project URLs); do not re-add them without a decision to publish. Dev tooling is a PEP 735 `[dependency-groups] dev` table, not an extra (`pip install -e . --group dev`), so it stays out of the installed metadata. `configs/`, `pddl/` and `experiments/` are **not** package data: the library and the CLI are what gets installed, and every documented command runs from inside the checkout.
- Main source code lives under `src/dias/`.
- PDDL assets live under `pddl/`.
- **`experiments/` is the entry point for running anything.** It holds the launchers (`launch.py`, `launch_threshold_validation.py`), the per-run and per-checkpoint validation steps (`validate_runs.py`, `validate_checkpoint.py`), the collector (`collect_results.py`), their shared `pipeline.py`, the Slurm job scripts in `slurm/`, the orchestration configs in `configs/`, the scaling study in `scaling/`, and `README.md`, the full recipes, which is the document a user is pointed at. It was consolidated from `scripts/`, `docs/experiments.md`, the root `scaling/` and three of the root `configs/` (2026-08-26). What stayed outside is what is not about running a sweep: the Lightning configs `dias fit` reads (`configs/main.yaml` and the `configs/experiments/*.yaml` overlays) and the domains (`pddl/`). Every documented command still runs from the repository root.
- **`experiments/pipeline.py` is the one place that resolves a path.** `EXPERIMENTS_ROOT` is its own folder and `PROJECT_ROOT` its parent; `SLURM_DIR`, `PIPELINE_CONFIGS` and `RESULTS_DIR` hang off the first, `CONFIGS_DIR` / `OVERLAYS_DIR` / `PDDL_DIR` / `LOGS_DIR` off the second. `OVERLAYS_DIR` (`configs/experiments/`) is the `dias fit` overlay folder and was called `EXPERIMENTS_DIR` before the consolidation; it was renamed because two different things called "experiments" in one module is how a wrong join gets written. `launch.py` reaches the job scripts through `SLURM_DIR`, never by joining `PROJECT_ROOT` itself.
- Collected result tables go to `experiments/results/<name>.md`, written by `collect_results.py --markdown` / `collect_scaling.py --markdown`. The folder is **gitignored**: every table in it is regenerated from `logs/`, and `.md` writers create the folder on first write, so a fresh clone needs no setup. Do not commit them, and do not point public docs at `local/`, which holds the paper PDF and working notes.
- **There is no per-domain manifest.** A domain *is* a folder under `pddl/`, and every file of it follows from the folder name: `domain.pddl`, the training instance `train.pddl`, the held-out `test-1.pddl` .. `test-3.pddl`, the STRIPS+ argument positions `strips+.yaml` (found beside the domain file by `schema/domain.py`) and the tuned `config.yaml`. `experiments/pipeline.py` is the one place that spells those names (`domain_pddl` / `train_problem` / `validation_problems` / `domain_config` / `available_domains`); nothing else joins a path by hand, and `pddl/domain-settings.yaml`, which used to repeat the layout as a list, is gone. Adding a domain is adding a folder.
- Per-domain training overrides live in `pddl/<domain>/config.yaml` (a Lightning partial config composed after `configs/main.yaml`). **A domain config selects its domain**: it opens with its own `domain_path` / `problem_path`, which is what completes the chain, since the base config supplies neither. Those two paths must be the folder's own `domain.pddl` and `train.pddl`, and `tests/test_configs.py` fails if they drift. Beyond them it carries only what differs from `main.yaml`: every domain sets `aux_loss_weight`, and the six that sample differently set the four `*_per_action_*` bounds. `launch.py` still appends absolute paths last, which override the relative ones for a Slurm job that does not run from the repository root.
- Per-experiment overlays live in `configs/experiments/{mlp,noise}.yaml`.
- Validation sweep settings live in `experiments/configs/validation.yaml`.
- Per-domain Slurm resources live in `experiments/configs/slurm-resources.yaml` (training array) and `experiments/configs/slurm-resources-validation.yaml` (validation array), both consumed by `experiments/launch.py`. Same schema (`defaults` + per-domain overrides), resolved independently; validation runs on CPU (DIAS/noise validators are CPU-only, the MLP-effects validator falls back to CPU), so it requests no GPU and targets all partitions.
- Training GPU requests are per domain and live entirely in `experiments/configs/slurm-resources.yaml`; treat that file as the source of truth rather than hardcoding a partition or GPU size here. It currently requests GPU shards (`gres: shard:N`) sized per domain from a shared `defaults` block, with no partition pinning. A domain that needs a whole GPU or a specific partition gets it via its own entry (`gres: "gpu:1"` and/or `sbatch_extra: ["--partition=<name>"]`).
- The current single-domain base training config in this workspace is `configs/main.yaml`. **It names no domain**: `domain_path` / `problem_path` have no default in it and none in `PddlGraphDataModule` either, so `dias fit --config configs/main.yaml` on its own is refused rather than silently training gripper, and every documented command pairs it with a `pddl/<domain>/config.yaml`. `tests/test_configs.py::RequiredValuesTest` pins that.
- **Where a default lives: each layer states only what it changes about the layer below, and the bottom layer is the class signature.** `DIAS` and `PddlGraphDataModule` default to the paper's full model with no noise, so `configs/main.yaml` was reduced (2026-08-27) to the run itself (trainer, logger, callbacks) plus the values a class cannot choose: `num_slots`, the τ schedule, and the four sampling bounds. Everything it used to restate moved into the signatures, at the values the paper runs at: `object_dim=32`, `learning_rate=0.005`, `aux_loss_weight=0.1`, `successor_relations=True`, `include_statics=True`, `batch_size=200`, `batch_sampling_strategy="stratified"`, and the ablation switches, `shuffle_train`, `num_workers`, `action_arguments`, `strips_plus_actions`, `num_train` / `num_valid`, `data.max_steps` at their previous values. Do not restate a default to make it visible: every argument is documented in its own signature and printed by `dias fit --model.help dias.models.DIAS` / `--data.help dias.data.datamodule.PddlGraphDataModule`, and each run saves the config it fully resolved to.
- **Every `__init__` argument of `DIAS` and `PddlGraphDataModule` carries a one-line description**, as a Google-style `Args:` block in the `__init__` docstring, which is what `--model.help` / `--data.help` print (jsonargparse reads it through `docstring-parser`). The five the CLI links from the datamodule say so, in the words "(linked from the datamodule)". A new argument gets its line in the same commit; the class docstring stays for what the arguments cannot say individually.
- **Two arguments have no default anywhere, because nothing can stand in for them**: `data.domain_path` and `data.problem_path`. `num_objects`, `relation_arities` and `num_actions` are required too, but only because the CLI links them from the datamodule. Arguments defaulting to `None` mean "not set" rather than a value: `num_slots` (an error unless `per_action_slots`), `precondition_tau` (no annealing), `noise` (clean transitions), `data.seed` (see below), and the four sampling bounds, which `SampleQuota` refuses as a group if nothing says how much to sample.
- **One seed per run.** `data.seed` defaults to `None`, meaning "whatever seeded this run": `CLI._seed_the_data_from_the_run` fills it in from `seed_everything` before anything is constructed, so the saved config records the number the walk actually sampled under, and a seed given explicitly still wins. `seed_everything` itself keeps its per-run draw, `random.randrange(2**32)` (the range Lightning accepts), so an unseeded run is still reproducible after the fact from the config it saved. `experiments/launch.py` and `experiments/slurm/train.sh` therefore pass `--seed_everything` alone; they used to pass `--data.init_args.seed` beside it, which was one value in two places and silent when one was forgotten. A datamodule built outside the CLI reads the same number off `torch.initial_seed()`, which `seed_everything` sets, so there is no second default to keep in step with anything.
- Standardized filenames per domain folder are `domain.pddl`, `train.pddl`, `test-1.pddl`, `test-2.pddl`, `test-3.pddl`, `strips+.yaml`, and `config.yaml`.
- The upstream instance generators (<https://github.com/AI-Planning/pddl-generators>) are **not** vendored. They are needed only to change the scaling study's size ladder, whose instances are committed; `experiments/scaling/generate_instances.py --generators-dir DIR` takes a checkout of them.
- `experiments/scaling/` is a self-contained one-off study of runtime and GPU memory versus instance size. It is intentionally *not* wired into `experiments/launch.py`; see "Instance-Size Scaling Study".

## High-Level Pipeline

The end-to-end DIAS pipeline is:

1. Load one PDDL domain and one problem instance.
2. Build symbolic transition samples from random-walk or BFS-based state exploration.
3. Convert symbolic states into adjacency-tensor and PyG graph representations.
4. Train the DIAS model with Lightning using stratified or random batching.
5. Recover learned lifted action schemas from trained model parameters.
6. Validate learned schemas by comparing reachable successor states against the original domain on held-out problems.
7. Run this per `(domain, seed)` pair for sweep experiments and log results to W&B plus local JSON summaries.

## Training Data Semantics

When working on data generation or dataset code, preserve these assumptions unless a task explicitly changes them:

- Only unary and binary predicates are supported.
- Action binding is assumed injective.
- Pure STRIPS-style action schemas are the default target.
- Domain predicates are assumed known.
- Training samples come from a single problem instance per domain.
- For full sweep experiments, training uses `pddl/<domain>/train.pddl`.
- Validation uses the three held-out instances `pddl/<domain>/test-{1,2,3}.pddl`. Which problems those are is the folder layout, not a setting: `experiments/configs/validation.yaml` holds the sampling knobs and the seeds, and no longer a `problem_offset` / `num_problems` slice.

## Core Code Map

- `src/dias/main.py`: Lightning CLI entry point for training.
- `src/dias/data/datamodule.py`: the Lightning datamodule: PDDL loading, metadata extraction, sampling constraints, and the dataloaders. It composes the modules below rather than implementing them.
- `src/dias/data/datasets.py`: `PddlTransitionDataset` (the sampled transitions as dense tensors) and the two views onto it: `PddlGraphDataset` (an index list) and `StratifiedActionIterableDataset` (an endless action-balanced stream). `_build_sample` is the one place a transition becomes the pair of PyG graphs a step consumes, and attaches the noise flip counts when the sample was corrupted.
- `src/dias/data/quota.py`: `SampleQuota`, the per-action sampling bounds, built by `with_floors` (which applies `min_per_action_*_floor`) and validated on construction. The datamodule's arguments stay flat, since that is what configs, sweeps and archived hyper-parameters name; the quota is derived from them and is what the sampler and the split read.
- `src/dias/data/splitting.py`: `cap_per_action`, `stratified_split` and `check_every_action_survives`, the action-stratified train/validation division, as functions of the action index tensor.
- `src/dias/data/generate_samples.py`: state-space exploration: `reachable_states` (a BFS over distinct states, which the validators sample from), `generate_random_walk` / `generate_bfs` (transitions as sample dicts), and `samples_to_tensors`. Sample dicts hold only primitives: nothing carries a live pymimir object across a module boundary.
- `src/dias/models/dias.py`: the LightningModule, holding the wiring, hooks, losses, and the two supported ways to read a trained model: `schema_logits()` (the lifted schema, arity-masked) and `effect_logits(adjacency, selection, y_action)` (the state-dependent effects the MLP-effects validator needs). Nothing outside `models/` touches `predictor`.
- `src/dias/models/encoder.py`: `RelationalEncoder` (was `gnn.GNNModule`), the relational convolutions, in `ModuleList`s, plus `initial_features` (where an object starts before message passing, and the `random_node_embeddings` ablation).
- `src/dias/models/objectives.py`: `DiasObjective`, the adjacency cross-entropy, the two auxiliary terms (each independently ablatable), and the Hamming diagnostic, returned as a `Losses` value whose `logged()` names them the way a run's history does. The auxiliary terms are returned *beside* `L_adj`, never summed with it: reconciling the two gradients is `pcgrad`'s decision.
- `src/dias/models/pcgrad.py`: `SingleObjective` / `WeightedSum` / `PCGrad` behind one `backward(primary, auxiliary, parameters)`, chosen once by `gradient_combiner(...)`. PCGrad takes the two **scalar losses**, not two gradient lists, because the auxiliary weight is applied inside autograd, which is what the archived runs did.
- `src/dias/models/edges.py`: `EdgeTypeLayout`, the only place that knows what an edge type id means. Four consecutive bands over `R` relations and `A` action-argument positions: the state's atoms, the same reversed, action self-loops, and (with `successor_relations`) what the transition changed. It builds the edges too, so `DIAS.forward` neither numbers nor assembles them. `src/dias/models/utils.py` no longer exists: the Sinkhorn iteration moved to `selection.py` and the change-edge construction here.
- `src/dias/models/prediction.py`: `SuccessorPredictor`, which composes selection, preconditions and effects into `A' = A + pre·Δ`. Holds no schema parameters of its own; it derives the object count from the input rather than being told it.
- `src/dias/models/selection.py`: `resolve_num_slots` (how many slots the model gets, given the widest action and what the instance can support; the one place that clamps) and `SlotSelector`, which holds the learned slot queries, the Sinkhorn assignment, per-action arity masking, forced action arguments, and `slot_weights` (which the auxiliary loss reads instead of the raw logits).
- `src/dias/models/effects.py`: `EffectSource` and its two implementations: `StaticEffects` (one learned tensor per action, the DIAS model) and `StateDependentEffects` (an MLP over the slot-projected state). The base class applies the arity mask, so neither can skip it; `action_logits()` returns `None` for the state-dependent one, which is how readers learn there is no lifted effect tensor rather than by hitting a missing attribute.
- `src/dias/models/masking.py`: `unary_offdiagonal_mask` / `forbid`, deciding which `(relation, slot, slot)` cells no lifted schema can express, and pinning them to the ignore channel. Applied in the forward pass, not baked into the parameter.
- `src/dias/models/outputs.py`: `Channels` (the one decoder of the 3-channel ignore/assert/negate convention), `SchemaPrediction` (what `SuccessorPredictor.forward` returns), `SchemaLogits` (what `DIAS.schema_logits()` returns).
- `src/dias/schema/domain.py`: `DomainSchema`, the frozen relation/action/object metadata of one `(domain, problem)` pair, built `from_pddl` or `from_checkpoint`. Consumers that only need metadata use this instead of constructing a datamodule. It also owns the functions that decide what that metadata *is*: `read_metadata` (a pymimir domain and problem as raw lists), `tensor_relations` (which predicates become channels of the adjacency tensor), `argument_positions` and `strips_plus_arguments` (which action arguments are observed). They lived in `data/` and `datamodule`, which made `schema` import `data` through four function-local imports; the dependency now runs one way.
- `src/dias/schema/action.py`: `ActionSchema` / `LiftedAtom`: a lifted action schema over slot indices, and its PDDL serialization.
- `src/dias/pddl/text.py`: pure PDDL string handling (paren balancing, block extraction, typed-parameter and type-hierarchy parsing, equality rewriting). Imports nothing.
- `src/dias/pddl/untype.py`: compiling typed PDDL to untyped PDDL: `extract_domain_header` and `strip_problem_types`, both text in / text out.
- `src/dias/pddl/transpiler.py`: `PDDLTranspiler`, from binarized schema tensors to `ActionSchema`s.
- `src/dias/pddl/states.py`: reading pymimir states (`state_fluents`) and re-hosting one problem's state on another (`transfer_state`).
- **Each validator module is named for the model it scores, and holds one class named the same way**: `validation/dias.py: DiasValidator` (reconstructs learned schemas from a checkpoint and compares successor-state behavior), `validation/mlp_effects.py: MlpEffectsValidator` (a checkpoint whose effects come from an MLP over the state, so only its preconditions become a learned domain) and `validation/l1.py: L1Validator` (a learned PDDL domain produced outside this repository). One name each, rather than three modules sharing one `ModelValidation`; `pipeline.Validator.class_name` is what says which to import, and the CLI keys `dias` / `mlp` / `l1` stay as they are, since they name experiment directories that already exist.
- `src/dias/validation/checkpoint.py`: `load_run`, which resolves a run's best checkpoint, filters retired datamodule hparams, absolutises its paths, and returns the model plus its `DomainSchema` as a `TrainedRun`.
- `src/dias/schedules.py`: `Constant` / `Exponential` / `PiecewiseLinear`: the τ schedule, as pure functions of the global step, plus `as_schedule` for the primitive form checkpoints store.
- `src/dias/adjacency.py`: the dense `[R, O, O]` representation: `valid_cells` (which cells a relation of a given arity may occupy), `adj_to_pyg_data`, and `dense_from_edges`, the one builder turning a PyG batch back into `[B, R, O, O]` (reached through `DIAS.dense`).
- `src/dias/hparams.py`: `to_mapping` / `from_mapping`: how a dataclass-typed argument (the τ schedule, the noise model) round-trips through hyper-parameters, which must hold primitives or `torch.load` refuses the whole checkpoint.
- `src/dias/data/noise.py`: `Ratio` / `ExpectedCount` (the two adjacency-noise models, each owning only its own parameters) and `RelationStats`, the per-relation true/false ratios and fluent flags they read.
- `src/dias/models/preconditions.py`: `Preconditions` (the learned precondition tensor, masked on the way out) and `soft_conjunction` (was `utils.gmean`), the relaxed product standing in for precondition satisfaction.
- `src/dias/models/checkpoints.py`: migration of pre-refactor checkpoints. **There are exactly two formats and one rule between them.** The published format is `CHECKPOINT_VERSION = 1`; an absent stamp is `UNVERSIONED` (0), the layout the paper's runs were written with. The refactor passed through several intermediate layouts, but none left the branch, so nothing can carry those numbers and no rule exists for them. `_from_unversioned` does all of it: the state-dict renames, the dropped derived keys, the final encoder convolution's unused bias (whose index is read off the state dict, since it follows `encoder_hidden_dims`), the τ schedule reconstruction, `parameter_plotting`, and the refusal of pre-activation MLP checkpoints. A stamp higher than the current one is refused rather than loaded as-is. **Migration is driven by the stamp, not by a failed load**: Lightning silently drops hyper-parameters it does not recognise, so a renamed one would otherwise fall back to its default and quietly change what an archived run means. **Version 1 is not released yet**: while this work is unmerged, another change to the layout extends `_from_unversioned` and `tests/test_checkpoint_layout.py` rather than bumping anything; nothing outside the branch carries a version-1 stamp. Once it lands on `main`, a change to what the model stores needs version 2 and a rule of its own, because editing this one would change what an already-published checkpoint means.
- `src/dias/reporting/`: `labels.py` (display names), `vega.py` (the three Vega-Lite heatmap specifications), `charts.py` (tables, and registering the specifications in the run's own entity) and `callback.py` (`SchemaChartCallback`, the Lightning callback that logs them). `src/dias/utils/` no longer exists, and neither does `plotting.py`: the schema is logged as the numbers it is made of, not as rendered images.
- `src/dias/validation/decoding.py`: `derive_schema`, which binarizes the learned schema tensors at a threshold, the paper's derivation of action schemas (Sec. 4.5). (Was `validation/utils.py::process_model_logits`.)
- `src/dias/validation/successors.py`: state sampling (`sample_reachable_states`, `transfer_states`, `resolve_sample_seed`) and behavioural scoring, shared by all three validators. **`score_successors` is the one scorer**: it takes per state the expected and produced successors keyed by action name, and all it requires is that equal successors compare equal: a pymimir state index for the symbolic validators, a binarized adjacency for the MLP-effects model, which has no lifted schema to ground. `compare_successors` is the symbolic front end to it. **It reports one measure, attributed to actions**: `tp`/`fp`/`fn` are the sums of `action_stats`, so a successor reached under the wrong operator is a false positive there and a false negative under the right one, and a successor two operators both reach is two predictions. There is deliberately no second, union-over-actions count beside it: the repository learns action schemas, not a bare transition model, and carrying both measures in one payload is what let the two be confused. The state-level question survives as `matches` / `accuracy` (the two successor *sets* agreed exactly), which holding everywhere is the same thing as the union view scoring perfectly.
- `src/dias/validation/artifacts.py`: `PddlWorkspace`, the self-deleting temp directory holding generated PDDL, since pymimir only parses from paths.
- `experiments/launch.py`: the single experiment launcher, structured as `parse_args -> build_plan -> describe -> execute`. `LaunchPlan` is the resolved launch and is where every rejection happens, so nothing reaches sbatch unless the whole grid is valid; the two backends (`submit_domain`, `run_domain`) take `(plan, point, domain)`. Per domain it submits a Slurm training array (one task per seed) plus a `--dependency=aftercorr` validation array, or runs the same steps sequentially with `--backend local`. Selects the experiment via `--experiment-type {dias,mlp,noise}`.
- `experiments/validate_runs.py`: compute-side per-`(experiment, domain, seed)` validation; picks the validator through `pipeline.EXPERIMENT_VALIDATOR` and writes the per-run JSON. Invoked by `experiments/slurm/validate.sh` and by `launch.py --backend local`. `--threshold` / `--results-experiment` support post-hoc re-validation (see below); the threshold guard reads `Validator.binarizes_schema` rather than testing the experiment type.
- `experiments/launch_threshold_validation.py`: re-validates the checkpoints of a finished experiment at several binarization thresholds, into sibling `logs/validation/<experiment>-thr<T>/` directories. Validation only, no training.
- `experiments/collect_results.py`: aggregates per-run results (local JSON or the W&B API) into a `P / R / N_S / N_C / N_SC` table per domain; with `--sweep AXIS` into a domain × swept-value matrix per metric, with `--threshold-sweep` into a domain × threshold matrix, optionally written out as markdown tables (`--markdown`). Without a sweep, `--experiment` accepts several unrelated experiment names (one table each).
- `experiments/validate_checkpoint.py`: the single-model validation entry point, `--validator {dias,mlp,l1}`. **L1 is reachable only from here, by design**: it scores a learned PDDL domain produced by another system, passed as `--learned-domain`, so it has no checkpoint, no run id and no `(domain, seed)` for a sweep to iterate over. It replaced three near-identical `experiments/validation/run_*.py` scripts that each hardcoded the sampling counts `experiments/configs/validation.yaml` also declares; the defaults now come from that config. This is the only way to reach the L1 baseline.
- `experiments/pipeline.py`: what every pipeline script shares: `PROJECT_ROOT` and the config paths, the domain-folder layout (`domain_pddl`, `train_problem`, `validation_problems`, `domain_config`, `available_domains`, `select_domains`), `load_yaml`, `run_command`, seed resolution, the sbatch flag builders (`format_array`, `resolve_resources`, `sbatch_resource_opts`, `sbatch_output_opt`, `prepare_slurm_logs`), the shared argparse blocks, the W&B identity, and `VALIDATORS` / `EXPERIMENT_VALIDATOR` (each entry naming its validator class, which `validator_class` imports). It imports neither torch nor pymimir, so submission works on a login node. `experiments/scaling/launch_scaling.py` imports its sbatch helpers from here rather than from `launch.py`'s privates; keep it that way.
- `experiments/scaling/`: the one-off instance-size scaling study (`generate_instances.py`, `benchmark.py`, `run_scaling.py`, `launch_scaling.py`, `collect_scaling.py`, `configs/{sizes,scaling}.yaml`, `slurm/benchmark.sh`). Separate from the main pipeline on purpose; see "Instance-Size Scaling Study".

## Training Conventions

- Prefer the installed CLI entry point `dias fit --config configs/main.yaml --config pddl/<domain>/config.yaml` for single-domain training unless a script explicitly uses `python -m dias.main`. The base config alone is not a runnable chain: it names no domain.
- Per-domain runs compose configs: `--config configs/main.yaml --config pddl/<domain>/config.yaml` (plus `--config configs/experiments/<type>.yaml` for MLP/noise). `experiments/launch.py` builds this chain and injects `domain_path` / `problem_path` / `seed_everything`.
- The per-step diagnostic formerly logged as `loss_mse` is `train/hamming_distance`: it is a count of cells the thresholded prediction got wrong, never an MSE and never trained on. Runs archived before the rename log it under the old key.
- The two precondition diagnostics are logged as `precondition_satisfaction` (the relaxed measure the loss sees) and `precondition_product` (the exact product, detached). They were `pre_mean` / `pre_prod_mean`, which is what archived runs log them under.
- The learned schema is reported by `SchemaChartCallback`, registered under `trainer.callbacks` in `configs/main.yaml`, not by the model, which no longer knows about plotting. Six panels (add/delete effects, positive/negative preconditions, `selection_samples` slot-to-object assignments per action from one validation batch, default 3, and slot weights) go out as `wandb.Table`s bound to one of the three Vega-Lite specifications in `reporting/vega.py` (`SCHEMA`, `SELECTION`, `SLOT_WEIGHTS`), every `log_every_n_validations` validation epochs (default 20) and once at `on_fit_end`. The selection grid is rectangular, so an action the batch holds fewer times than `selection_samples` narrows it for every action rather than making it ragged. Nothing in a specification is titled (the values along an axis say what it holds), and every chart states `vega.CELL`, so a value cell is square and the same size in all of them. Selection and slot weights are separate charts because a Vega-Lite `facet` takes only a unit or layer spec, never a concat, so the side-by-side pairing the matplotlib figures drew per action cannot be expressed without putting the weights on an axis that says it holds objects. Without a W&B logger it logs nothing.
- **Four details of the panel W&B renders are not in the SDK's surface; they were read off the config W&B's own chart editor writes, and a rename upstream would break them silently.** `wandb.plot_table` binds a panel to `summaryTable`, which holds only the last table logged under a key, so `charts._spec_class` subclasses `CustomChartSpec` instead and rewrites the query to `historyTable` with its `extraKeys` and `index` arguments, plus the panel setting `showStepSelector`. All are needed: without `index` the panel has no step to draw and comes up **empty**, and without `showStepSelector` there is no slider. W&B rewrites a panel's configuration on **every** log, so anything in it that names the newest step points the page at a table that is still uploading, which made a live run's panels blink in and out. Two consequences, both deliberate: the editor's `defaultViewedStepIndex` (the slider's opening position) is left out, and `index` is fixed at the **first** step logged (`SchemaChartCallback._panel_step`) rather than tracking the latest, so the configuration stops moving. The slider opens on the first logged schema and reaches the rest. If W&B renames any of these the slider goes away; the charts themselves keep working.
- A colour bar is suppressed with `"legend": false`, not the `null` the Vega-Lite schema specifies: W&B draws the bar anyway for `null`, and for a spec-wide `config.legend.disable`. It warns about the type and honours the value.
- The specifications live in the *run's own* entity, so no clone depends on a preset saved in someone else's account. `charts.register` lists what is there (`customCharts`) and creates or updates only what differs: **`wandb.Api().create_custom_chart` cannot update**, so without the `updateCustomChart` mutation beside it an edited specification would never reach W&B and the old chart would be drawn forever. That mutation wants the access level upper-cased; the SDK's `create` does that for you. If W&B cannot be reached the ids still follow from the names, and only the drawn panel suffers; the tables are logged either way.
- The selection panel comes from a real validation batch: the callback re-runs the forward pass inside `torch.random.fork_rng`, because `initial_features` draws from the global generator and a diagnostic must not shift a run's random stream. Before this the panel silently showed a *training* batch.
- Runs no longer log `noise/*` metrics. `ExpectedCount` spends a fixed Poisson budget per adjacency tensor, so the flip counts were a constant plus jitter; the per-sample counters that fed them are gone from `data/datasets.py` too.
- The default logger is W&B, declared in `configs/main.yaml` under `trainer.logger` with `project: dias`, `save_dir: logs` and **`entity: null`**, meaning the logged-in account or `$WANDB_ENTITY`. `src/dias/main.py` names no logger at all, so `dias` without a config falls back to Lightning's own. No account appears anywhere in the code; the scripts read `WANDB_ENTITY` / `WANDB_PROJECT` from the environment (`pipeline.py`).
- Sweep runs use a deterministic W&B run id `<experiment>-<domain>-s<seed>` (see `validate_runs.run_id_for`) so the validation array can locate each checkpoint without an id handoff.
- Training checkpoints are expected under `logs/dias/<run_id>/checkpoints/`.
- Validation code looks for a checkpoint matching `best-epoch*.ckpt`; preserve this naming unless the validation loader is updated in the same change. When a run id is reused (a re-run of one seed), several such files can coexist because Lightning suffixes the clash with `-v1`, so `validation/checkpoint.resolve_best_checkpoint` picks the newest by mtime; every validator reaches it through `load_run`.
- `src/dias/main.py` links datamodule metadata such as numbers of objects, actions, and relations into model init args through LightningCLI. Keep these interfaces synchronized.
- The default batching strategy is `stratified` (`PddlGraphDataModule`'s own default), which yields an effectively unbounded iterable dataset; training length is therefore controlled by `trainer.max_steps` and related trainer limits, not dataset exhaustion.
- Noise ablations: `data.init_args.noise` is one of the two dataclasses in `src/dias/data/noise.py`, configured by `class_path` / `init_args`: `Ratio(remove, add)` flips each eligible cell independently, `ExpectedCount(removed_atoms, added_atoms, fluents_only)` spends a Poisson budget per adjacency tensor. Unset means no noise; there are no cross-model parameters to keep at zero. The `noise` experiment overlay selects `ExpectedCount`.
- `configs/experiments/noise.yaml` also carries the paper's noise-experiment training adjustments (Appendix A.4.2): `min_per_action_train_floor: 200` / `min_per_action_valid_floor: 100`, `batch_size: 50`, and a floor of 0.1 on the precondition-aggregation parameter τ. The matching schema-derivation threshold of 0.75 is validation-side (see Validation Conventions).
- τ (`model.init_args.precondition_tau`) is the root degree of the geometric mean that stands in for the true precondition product. It is one of the schedule classes in `src/dias/schedules.py` (`Constant`, `Exponential`, `PiecewiseLinear`), configured by `class_path` / `init_args`. `Exponential` is `floor + (start - floor) * factor ** (step / every)`: it falls by `factor` every `every` steps, from `start` toward `floor`, without reaching it. Rate and asymptote are independent, so the noise overlay differs from `main.yaml` in exactly one number: `floor: 0.1` instead of `0.0`, because the exact product is too strict a precondition check under noise. There is no separate offset parameter, and no value that has to be recomputed when the floor moves; earlier revisions had both.
- Schedules are pure functions of the global step, queried where the value is used. They hold no state, so nothing has to be "advanced" before a read.
- `min_per_action_train_floor` / `min_per_action_valid_floor` raise (never lower) the per-domain `min_per_action_*`. Experiment overlays are composed *after* `pddl/<domain>/config.yaml`, so a plain `min_per_action_train` there would also shrink the domains that sample more; the floors express "raise the smallest per-action minimum" instead. They are applied by `SampleQuota.with_floors`, so `hparams` keep the raw per-domain values.
- The MLP-effects model is trained by adding `model.init_args.state_dependent_effects: true` (the `configs/experiments/mlp.yaml` overlay). Its effect MLP has SiLU activations between its linear layers, and its output goes through the same arity mask as the static effect tensor. Neither was true of the runs behind the paper's MLP column: without activations the MLP was one affine map, and without the mask it emitted effects relating two different slots through a unary relation. **MLP-effects checkpoints from before that are refused on load** (`models/checkpoints._migrate_state_dict`, with the reason in the message): those runs have to be retrained and revalidated before their numbers are quoted again. DIAS runs are unaffected: the change is confined to the effect source and the mask was already applied to the DIAS tensors, just at construction time.
- Model ablation switches are `model.init_args` arguments of `DIAS`, all defaulting to the full model, so `configs/main.yaml` does not list them and an overlay states only the one it turns off. Each toggles one component:
  - `use_slot_weights: false` forces all M slots active (no learned slot activation); also fixes the slot weights to 1 in the precondition aux term.
  - `use_precondition_loss: false` drops L_pre (the restrictive-precondition aux term).
  - `use_effect_loss: false` drops L_eff (the minimal-effects aux term).
  - `use_pcgrad: false` replaces PCGrad projection with a plain weighted sum `L_adj + α·L_aux` (same α).
  - `random_node_embeddings: false` starts every object node from an all-zero embedding instead of seeding the first half of the feature dimension with `0.1 * randn`, so symmetric objects stay indistinguishable to the GNN.
  - Ready-made overlays live in `configs/experiments/ablation-*.yaml` (composed last on top of `main.yaml`): `ablation-no-slot-weights`, `ablation-no-precondition-loss`, `ablation-no-effect-loss`, `ablation-no-aux-loss` (drops both aux terms, i.e. α = 0), `ablation-no-pcgrad`, and `ablation-no-random-embeddings`.

- **The last encoder convolution has no bias** (`RelationalEncoder.__init__` passes `bias=index != last`). Nothing is normalised after that layer, so a bias there would add the same vector to every object embedding; the slot scores are a plain inner product, so it reaches the assignment as a per-slot constant, and Sinkhorn's row scaling removes it exactly. The loss could not see it: its gradient was float32 round-off around 1e-10, six orders below any other parameter's, which Adam normalised into full-size steps in whatever direction round-off chose. That made the training trajectory unreproducible across machines. Checkpoints written before this carry a learned value for it; migration 4 drops it, which is safe precisely because no gradient ever reached it (verified on a paper checkpoint: discarding a trained bias of 0.02 moves the predicted adjacency by 2e-12).
- **What reproducibility this repository promises.** A training run repeats exactly only under `--trainer.deterministic=true` (Lightning's own flag: it calls `torch.use_deterministic_algorithms(True)` and sets `CUBLAS_WORKSPACE_CONFIG`); do not add a second flag for it. Off by default, because it raises on any operation without a deterministic implementation and that is a poor way for a 130-run sweep to fail (`warn` is the middle setting). Measured: on GPU, three runs of one seed give three different results without it and one result with it, at no throughput cost (82–94 ms/step on gripper either way, inside the run-to-run spread). On CPU it is thread-count that decides: 1, 2, 4 and 8 threads give four different trajectories with *or* without deterministic mode, because float addition is not associative and the thread count decides how a parallel reduction is split.
- The training-trajectory golden (`tests/test_training_characterization.py`) pins every parameter after three real steps. It needs `torch.set_num_threads(1)` (set at module import, so the fixture holds on machines with different core counts) *and* asks for `deterministic=True` on its Trainer, restoring the global flag afterwards. **The fixture is a regression guard, not a link to the paper's runs**: it was regenerated once, deliberately, when `DIAS.__init__` started building modules in the order the data flows (edges → encoder → prediction), which changes what a seed draws. Nothing was lost: no archived GPU run was reproducible from its seed either. **It compares the trajectory at `TRAJECTORY_TOLERANCE` (1e-4), not the `TOLERANCE` (1e-6) the forward golden uses**, because Adam turns a relative gradient perturbation into an absolute parameter difference of about `lr` times its size, whatever the gradient's own magnitude: two CPUs that dispatch different vectorized kernels then part by ~1e-6 over three steps, which is what made one job of the CI matrix red on the runner it happened to draw. Measured: the same three steps taken through torch's scalar CPU kernels rather than its vectorized ones land up to 5.2e-5 from the fixture, while the forward golden moves 1.5e-8 across that same pair of paths and keeps the tight tolerance. Three steps move every parameter by 0.024 to 0.030, so the wider tolerance still sits 300 times below anything a real behaviour change moves.
- **Module construction order is no longer load-bearing.** It used to be pinned so an archived seed could be re-derived; it now reads in data-flow order, and `SuccessorPredictor.forward` groups by concept (bind slots → do the preconditions hold → what does the action change) rather than ordering projections to fix autograd's accumulation. Verified behaviour-preserving with parameters set independently of construction: the forward output is bit-identical and gradients differ by ≤6.4e-10 (relative 5e-7), which is the accumulation-order round-off and nothing else.
- **A test module is named after the module it covers**, minus the package path: `tests/test_noise.py` for `data/noise.py`, `tests/test_mlp_effects.py` for `validation/mlp_effects.py`, `tests/test_generate_samples.py` for `data/generate_samples.py`. The two golden files say which path they pin, `tests/test_training_characterization.py` and `tests/test_validation_characterization.py`.
- The test suite must run on the oldest supported Python (3.10). `unittest.TestCase.enterContext` is 3.11+; use `tests/support.temp_dir(self)` for a self-cleaning temporary directory instead. CI runs 3.10–3.13, so a 3.11-only API in a test is caught rather than assumed. `.github/workflows/ci.yml` runs three jobs: `format` (black / isort), `test` (an editable install with the dev group, then pytest), and **`install`**, which builds an *empty* virtual environment per interpreter, does a non-editable `pip install .`, and then runs `dias --help` and imports the package **from another directory**, so a dependency with no wheel for one Python, or a module missing from the installed copy, fails there rather than on a user's first clone. It deliberately runs no training: `configs/`, `pddl/` and `experiments/` are not packaged. A Python version that cannot install is dropped from the matrix, from `requires-python` and from the README together. isort's `src_paths` lists `experiments` **and** `experiments/scaling`: the scaling scripts import each other as siblings after inserting their own directory on `sys.path`, and without the nested entry isort files those imports as third-party and the `format` job fails.

## What a Run Reports

- **The library configures no logging.** Every module reports through `logging.getLogger(__name__)`, and only an entry point installs a handler: `dias.main.main` for training, `pipeline.configure_logging` for the scripts. That is what keeps `dias` importable inside someone else's application, and it is why `src/` contains no `print`.
- The scripts take `-v` / `-q` (`pipeline.add_logging_arguments`), and `DIAS_LOG_LEVEL` overrides both, which is how a Slurm job, whose command line is fixed by `experiments/slurm/*.sh`, is made verbose.
- **INFO is for state changes someone waits on, once each; anything per-step or per-batch is DEBUG.** Messages carry their values as `%s` arguments, never as an f-string, so a suppressed line costs nothing to format.
- The line-up of a training run, in order: the composed config chain and the resolved domain/problem (`dias.run`, logged before anything slow starts), the model summary (slots, parameter count, effect source, which auxiliary terms are live, the gradient combiner), then the sampling target, the walk's own periodic progress, the split, and where the run is being written. Validation adds, per problem: the states sampled, the schemas read off the checkpoint at that threshold, and the resulting precision/recall.
- `data/generate_samples._Progress` reports at most every `PROGRESS_INTERVAL_SECONDS` (10 s) and never before the first interval has passed, so a long random walk or BFS says where it is while a short one stays silent.
- `pipeline.run_command(cmd, dry_run, capture=True)`: sbatch needs the captured job id, a local training run needs the opposite. `launch.py --backend local` passes `capture=False` so the child inherits the terminal; with the default it ran for hours in silence and then threw its output away.

## Validation Conventions

- Validation is behavior-based, not string-based. The important metric is whether the learned domain produces the same successor states as the original domain.
- For DIAS checkpoints, `DiasValidator` reconstructs learned lifted schemas from model logits and merges them with transformed original actions into temporary untyped PDDL files.
- Validation samples states from held-out problems and compares original versus learned reachable successor sets. **The draw is not fixed to a constant, but it is always recorded.** `experiments/configs/validation.yaml: sample_seed` is null, so each run scores on its own sample, as each run also trains on its own; `successors.resolve_sample_seed` then *draws* a seed, every validator stores it as `self.sample_seed`, and the result JSON carries it. Passing it back reproduces exactly those states, which is what `tests/test_validation_characterization.py` pins. `validate_runs` resolves once per run, so a seed's problems share one draw. The generator is the validator's own, never the global `random` module, so it neither depends on nor disturbs anything else's random state. Results written before this record `sample_seed: null` and cannot be reproduced.
- Precision and recall are **micro-averaged over per-action counts**: every validator returns `tp`/`fp`/`fn` (the sums of its `action_stats`) next to the rates, and `collect_results._seed_precision_recall` sums those across a seed's problems rather than averaging per-problem precisions. Archived results carry `action_stats` and no totals, so that path reduces them by summing the same counts: the fallback is an identity now, not a second estimator. **All three validators emit the same payload**, `action_stats` included; the MLP-effects validator used to be alone in omitting it, because it scored its own successors. **The union-over-actions measure was dropped rather than reported beside this one** (2026-08-26): measured over all 3348 archived per-problem results, the two agree on 3330 and never disagreed about whether a run was sound or complete, and where they part the attributed one is the claim the paper makes: `abl-no-pcgrad/sokoban-pull` seed 1 reproduces 12% of transitions under the union view and 0% under this one, having permuted the operators.
- **The MLP-effects validator is the only validator with parallelism, and that is not an oversight.** Its per-state work is grounding the learned domain plus a batched forward pass, and `num_workers` spreads it; DIAS and L1 validate 250 states in about six seconds even on the largest domains (measured on archived `dias-full` checkpoints: driverlog test-3 6.6 s, logistics test-3 5.7 s), and a sweep already runs 130 of those in parallel as Slurm array tasks. Adding worker processes there would buy seconds and cost the payload/reconstruct machinery that exists only because pymimir states cannot cross a process boundary.
- Sweep validation writes local results to `logs/validation/<experiment>/<domain>/seed<seed>.json` and mirrors numeric metrics to the resumed W&B run under `validation/<problem_stem>/...`.
- A trained model's schema is read through `DIAS.schema_logits()` and nowhere else. It returns the effect and precondition logits **with the arity mask already applied**, plus the slot-weight logits, on the CPU. Reading `model.predictor.*` directly is wrong: since the mask moved into the forward pass, the raw parameters hold untouched noise at cells no lifted schema can express, and a reader that softmaxes them finds effects the model never applies. Checkpoints written before that still carry `-inf` there, which the mask leaves as it is.
- `schema_logits().effects` is `None` for a model whose effects come from the state (`state_dependent_effects=True`). That is what the MLP-effects validator's guard checks, what makes the heatmap callback skip the effect panels instead of crashing, and what `decoding.derive_schema` takes to mean "no lifted effects to read": it returns `None` for the add and delete arrays rather than being fed a `zeros_like` decoy.
- A caller that already knows the slot binding (the MLP-effects validator, which got it by grounding the learned action through pymimir) asks `DIAS.apply_schema(adjacency, selection, y_action)` for the successor. It does **not** consult the preconditions: applicability was already decided by the grounding, and deciding it twice by two different means is how the two used to disagree. `DIAS.retarget(num_objects)` records a new instance size and refuses one with fewer objects than the model has slots, replacing a silent assignment to `model.num_objects`.
- Reading a schema off a checkpoint binarizes the slot activations and the add/delete/positive/negative tensors at a single threshold, `validation.decoding.derive_schema(threshold=0.5)`. 0.5 is what the paper reports for the main experiments; `validate_runs.py --threshold` overrides it (DIAS validator only; the MLP-effects model has no schema to binarize and rejects a non-default value). The threshold applies uniformly: lowering it activates more slots (higher learned arity) *and* adds both effects and preconditions.
- The threshold of a launch is chosen per experiment type in `launch.SWEEP_AXES`' neighbour `VALIDATION_THRESHOLD` (`DEFAULT_VALIDATION_THRESHOLD = 0.5`, `noise` = 0.75 as in the paper), overridable with `launch.py --validation-threshold T`. It is exported to `experiments/slurm/validate.sh` as `THRESHOLD` only when it differs from 0.5, and passed to `validate_run(threshold=...)` on the local backend.
- `validate_runs.py --results-experiment NAME` redirects only the output directory (and W&B group) to `logs/validation/<NAME>/`, while the checkpoint is still located via `--experiment`. That is what keeps a re-validation from overwriting the original run's JSONs; the written JSON records the `threshold` it used.
- If checkpoint layout, run directory layout, or logger naming changes, update validation loaders and sweep scripts together.

### Threshold Re-Validation

- `experiments/launch_threshold_validation.py` re-runs *only* the validation step of a finished experiment once per threshold, on the checkpoints that experiment already produced. Per `(domain, threshold)` it submits one array over the seeds through the same `experiments/slurm/validate.sh` (no training, no `aftercorr` dependency); `--backend local` runs them sequentially.
- Results go to `logs/validation/<experiment>-thr<T>/<domain>/seed<seed>.json` (`launch_threshold_validation.threshold_experiment_name`, `%g` formatting, so `0.5` → `-thr0.5`). Each is an ordinary experiment directory downstream. The source `logs/validation/<experiment>/` is never written to.
- Default grid `THRESHOLD_VALUES = (0.1, 0.25, 0.5, 0.75, 0.9)`; 0.5 is re-run rather than reused so every column comes from the same code path and the same random state sampling.
- W&B logging is forced off (`NO_WANDB=1`): `validate_runs._log_to_wandb` mirrors metrics by *resuming* the training run, so a second threshold would overwrite the 0.5 numbers in that run's summary. The JSONs are the source of truth.
- The launcher refuses to submit when a `(domain, seed)` has no `best-epoch*.ckpt` (`--allow-missing` overrides). `--time` / `--mem` override the per-domain values from `experiments/configs/slurm-resources-validation.yaml` for every array.
- `experiments/slurm/validate.sh` reads the optional `THRESHOLD` / `RESULTS_EXPERIMENT` / `NO_WANDB` environment variables; unset means plain validation of a fresh run, so the normal pipeline is unaffected.
- Aggregate with `experiments/collect_results.py --experiment <experiment> --threshold-sweep [T ...]`, which rebuilds the column names with the same `threshold_experiment_name` (imported, not re-derived; keep it that way) and prints/writes the same domain × value matrices as `--sweep`.

## Sweep Conventions

- `experiments/launch.py` is the authoritative sweep launcher. Per domain it submits a training array (`experiments/slurm/train.sh`, one task per seed) and a dependent validation array (`experiments/slurm/validate.sh`, `--dependency=aftercorr`). `--backend local` runs the same steps sequentially.
- One run corresponds to one `(domain, seed)` pair; seeds default to `0 .. num_runs-1` (`--num-runs`, default = `len(experiments/configs/validation.yaml seeds)`).
- `--seeds` runs an explicit seed subset instead (single values and/or inclusive ranges, e.g. `--seeds 3 7-9`), which is how individual failed seeds are re-run. It is mutually exclusive with `--num-runs`. The Slurm array task id *is* the seed, so a subset becomes a sparse array spec (`--array=3,7-9`) and the `aftercorr` dependency still pairs the train/validate tasks of each seed. Re-running under the same `--experiment` reuses the run id `<experiment>-<domain>-s<seed>`, so the replacement run reuses that seed's checkpoint directory and overwrites its result JSON. Lightning does not delete the failed attempt's checkpoint; it writes the new one alongside with a `-v1` suffix, so validation resolves the *most recently written* `best-epoch*.ckpt` (see below) rather than an arbitrary glob hit.
- All runs of one launch share an `--experiment` name (= W&B group = results directory). `--experiment-type {dias,mlp,noise}` picks the overlay, the validator, and the validation threshold (0.75 for `noise`, else 0.5; `--validation-threshold` overrides).
- `--ablation {no-slot-weights,no-precondition-loss,no-effect-loss,no-aux-loss,no-pcgrad,no-random-embeddings}` composes one `configs/experiments/ablation-*.yaml` overlay on top of the experiment type (orthogonal axis; always uses the DIAS validator). Default: none (full model).
- `--sweep AXIS [--sweep-values V ...]` sweeps one hyperparameter: the whole domain × seed grid is submitted once per value, each into its own sub-experiment `<experiment>-<tag><value>` (`launch.sweep_experiment_name`, value formatted with `%g`, so `1.0` → `aux1`). Every point of the grid is submitted, including one that happens to match a value another experiment already ran: a column collected from runs launched under a different chain is a column nothing pins to this axis. The axes live in `launch.SWEEP_AXES` (`name → SweepAxis(param, tag, values, cast)`):
  - `aux-loss-weight`: `model.init_args.aux_loss_weight`, tag `aux`, grid `0.01, 0.03, 0.1, 0.3, 1.0`.
  - `num-slots`: `model.init_args.num_slots`, tag `slots`, grid `5, 7, 9`.
  - `tau`: `model.init_args.precondition_tau.init_args.every`, tag `tau`, grid `0, 100, 500, 1000, 5000`. (Was `gmean-temperature` / `gmeanT`, then `tau` / `tauT`; the trailing `T` was the schedule field's own former name, which is `every` now. The sweep directories under `logs/` were renamed each time, so an already collected sweep still collects; the result JSONs still record the experiment name their run was launched under.)
  - `dataset-size`: `data.init_args.min_per_action_train`, tag `n`, grid `20, 50, 100, 200, 500, 1000, 2000` (see below).
- The `dataset-size` axis is the one axis that moves several parameters at once (`SweepAxis.linked` → `launch._dataset_size_overrides`). For value N it pins `min_per_action_train = max_per_action_train = N` and `min_per_action_valid = max_per_action_valid = N/2`, which makes the sampled pool *exactly* `num_actions · 1.5N` transitions instead of a lower bound; the 2:1 train:valid weight then splits it into ≈N train / ≈N/2 valid per action (the ratio is enforced pool-wide, so individual actions drift a few percent). It also pins `min_per_action_train_floor` / `min_per_action_valid_floor` to the same values, which neutralizes the 200/100 floors in `configs/experiments/noise.yaml`: those are composed after the domain config and would otherwise clamp the 20/50/100 points back up under `--experiment-type noise`. No column reproduces a domain's default run, since the per-domain configs pair a tuned minimum with a loose cap. `--set` is rejected for *any* of the six keys, not just the axis parameter (`launch._axis_params`).
- Sweep overrides are appended last on the Lightning command line, so they beat the per-domain values in `pddl/<domain>/config.yaml`. Every axis is a plain `--key=value`, `tau` included: the schedule is a typed dataclass, so setting one of its fields is an ordinary jsonargparse sub-key override and leaves the others alone. `--experiment-type noise --sweep tau` therefore works, overriding `every` on top of the overlay's `start` / `floor`.
- `0` on that axis means τ sits at its `floor` from step 0, the `every` → 0 limit of the decay. With the default floor of 0 that is the regime where the divisor `1 + τ·(n-1)` in `soft_conjunction` becomes 1, i.e. the *exact* precondition product rather than a relaxation. `Exponential` handles it directly (the general form would divide by `every`).
- **One caveat on typed config values.** jsonargparse *merges* a configured value's fields onto the default's rather than replacing, so a schedule-typed argument must default to `None` (meaning `Constant(1.0)`), never to an instance; and switching the schedule *class* on the command line when a config file already names a different one does not work. Keep sweeps to field overrides.
- A sweep is rejected together with `--set <swept param>=...`; the `aux-loss-weight` axis is additionally rejected with `--ablation no-aux-loss`. Each sub-experiment is an ordinary experiment downstream (own W&B group, own `logs/validation/<sub-experiment>/` directory); nothing in `validate_runs.py` or the Slurm scripts knows about sweeps.
- Domain-specific sample bounds come from `pddl/<domain>/config.yaml`; the domain and problem paths from the folder layout via `pipeline.py`; per-domain Slurm resources from `experiments/configs/slurm-resources.yaml`.
- Global validation settings such as number of validation problems and sampling counts come from `experiments/configs/validation.yaml`.
- `experiments/collect_results.py` aggregates a finished experiment (local JSON or W&B) into the paper table. `--sweep AXIS [--sweep-values V ...]` rebuilds the sub-experiment names with the same `launch.sweep_experiment_name` and `launch.SWEEP_AXES` (imported, not re-derived; keep it that way) and prints a domain × value matrix per metric plus an `n` matrix; `--markdown <path>` writes the same matrices as markdown tables (one table per metric, raw values).
- Without a sweep, `--experiment` takes any number of unrelated experiment names (e.g. a baseline plus its ablations). Each gets its own printed table; `--markdown <path>` then writes one document: a cross-experiment summary table over the pooled seeds, followed by one domain table per experiment. All tables span the union of the domains (`-` for a domain an experiment lacks), and the summary's `n` column reads `<collected>/<expected>`, where expected is the per-domain seed count of the most complete experiment in the set. A sweep still takes exactly one `--experiment` (its base name) and is rejected with several. This is what generates the cross-ablation summary table.
- `experiments/slurm/train.sh` and `experiments/scaling/slurm/benchmark.sh` export `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`. Co-tenants on a shared GPU see the *reserved* pool, not the allocated one, so the fragmentation gap that setting closes (satellite reserved ~15.7 GB for ~5.7 GB of live tensors, visitall ~10 GB for ~4 GB) is what decides whether the per-domain `shard:N` reservations in `experiments/configs/slurm-resources.yaml` hold. The scaling study sets the same value, so the memory numbers it reports are the ones real training sees.
- The Slurm scripts under `experiments/slurm/` (and `experiments/scaling/slurm/benchmark.sh`) open with a block marked `── site configuration ──` holding every line specific to one cluster: the `#SBATCH` partition/QoS fallbacks and `DIAS_ENV_SETUP`, an overridable shell snippet that replaced the hardcoded `source ~/.zshrc && conda activate ddl`. Nothing below the end marker is site-specific. The scripts stay thin and defer experiment semantics to Python scripts and YAML configs.
- Nothing in the Slurm path assumes the submission directory. Slurm runs a batch script from a spool copy, so the launchers pass the script path and `--output` as absolute paths and export `DIAS_ROOT`, which the scripts use to locate `validate_runs.py` / `run_scaling.py`. `logs/slurm` is created under `--log-dir`.

## Instance-Size Scaling Study

`experiments/scaling/` is a self-contained one-off analysis: iterations per second and peak GPU memory as the *instance* grows, on `blocks-3`, `logistics`, `delivery` × 6 sizes × 3 seeds. It produces timings, not schemas: no checkpoints, no validation, no W&B. Documented for users in `experiments/scaling/README.md`.

- It measures the ordinary training path: `experiments/scaling/benchmark.py` instantiates `dias.main.CLI(run=False)` on the real config chain (`configs/main.yaml` → `pddl/<domain>/config.yaml` → `experiments/scaling/configs/scaling.yaml`) and attaches a timing callback. Nothing is stubbed or reimplemented; if the training step changes, this measures the new one.
- Runs are cut to `warmup_steps + measure_steps` (20 + 100, from `experiments/scaling/configs/sizes.yaml`), not the 10 000 steps of a real run. The warm-up steps are discarded, `torch.cuda.reset_peak_memory_stats()` is called right after them, and every step is bracketed by `torch.cuda.synchronize()`. `iterations_per_second` is `1 / median(step time)`.
- `experiments/scaling/configs/scaling.yaml` is the overlay that holds everything but the instance fixed: exactly 100 train / 50 valid transitions per action (pinned min *and* max, so delivery does not sample 10× more than blocks-3), batch size 200, and validation / logging / checkpointing off. Sampling time is timed separately by wrapping `datamodule.setup`: a Lightning `Callback.setup` hook runs *after* the datamodule's and would measure nothing.
- Ladder and Slurm resources live in `experiments/scaling/configs/sizes.yaml`. Instance ids encode the object count (`n0068`), which `experiments/scaling/generate_instances.py::OBJECT_COUNT` derives from the generator parameters and cross-checks against the parsed instance. Each size entry also carries a `target`, the shared ladder rung, because the domains scale in different units and cannot all hit the same count (logistics lands on 21/38/67/103/147). `run_scaling.ladder_for` pairs the two, and that pairing is what aligns the columns in `collect_scaling.py`; the exact counts get their own table.
- `experiments/scaling/instances/<domain>/n<objects>.pddl` plus `index.json` are generated once and **committed**; running the study needs neither the submodule nor the generator toolchain. `experiments/scaling/generate_instances.py` rewrites generator output into the repo's domain dialect (blocksworld: `- object` typing plus the reflexive `(eq b b)` facts the repo domain's `(not (eq ?x ?y))` preconditions require; logistics: `OBJ` → `object`, `in-city` → `loc`, added `(vehicle ?v)` facts; delivery: unchanged but renamed). The delivery generator needs `tarski` and runs from a gitignored venv at `experiments/scaling/.venv-delivery`.
- Layout mirrors the main pipeline: `launch_scaling.py` (submit) → `slurm/benchmark.sh` (array task) → `run_scaling.py` (one domain's ladder for one seed) → `benchmark.py` (one point) → `collect_scaling.py` (tables). It imports `_format_array` / `_sbatch_resource_opts` from `experiments/launch.py` rather than re-deriving the sbatch flags; keep it that way.
- Two deliberate departures from `experiments/launch.py`: an array task is one **(domain, seed)** and walks the whole ladder (so one curve is measured on one physical GPU), and it requests an **exclusive** GPU on a **pinned** partition (`gres: gpu:1`, `--partition=rleap_gpu_24gb`) instead of a `shard:N` slice: co-tenants on a shared GPU would land in the throughput numbers, and mixed GPU models would make a curve meaningless. Re-running on a different card belongs in a different `--experiment`.
- Each size runs as its own subprocess so a CUDA OOM costs one point, not the ladder. OOM is a recorded outcome (`status: "oom"`, exit 0), shown as `oom` by `collect_scaling.py`; a non-zero exit is a real failure. Memory is quadratic in objects, so the top of the `delivery` ladder is expected to exceed 24 GB.
- Results: `logs/scaling/<experiment>/<domain>/<instance>-s<seed>.json` (under the gitignored `logs/`).

## Paper-Level Modeling Notes

Use these as conceptual ground truth when reasoning about intended behavior:

- If the summary in this file is not enough, consult the paper: <https://arxiv.org/abs/2605.13282>. A local copy may be at `local/dias-paper.pdf`, which is gitignored and absent from a public clone.
- DIAS learns lifted positive preconditions, lifted negative preconditions, add effects, and delete effects.
- Object selection is performed via a GNN plus query-slot matching with a rectangular Sinkhorn-style assignment.
- Slot activations determine learned action arity.
- Successor-state prediction is trained from observed state transitions.
- Auxiliary losses encourage minimal effects and restrictive preconditions, while PCGrad-style handling prevents auxiliary objectives from overriding the main prediction objective.
- Evaluation is based on soundness and completeness of induced successor-state behavior on held-out problems.

## Naming

**Code names follow the paper's, and a new name is chosen by looking the concept up there first.** The pipeline was swept for this (2026-08-27), so a name that disagrees with the table below is a bug in the name, not a second convention:

| Paper | Code |
| --- | --- |
| relations / predicates `p`, arity `\|p\|` | `relation_names`, `relation_arities` (never `arity_relations`) |
| action schema `a`, arity `\|a\|` | `action_names`, `action_arities` |
| keys `K` | the encoder's `node_embeddings` |
| queries `Q^a` | `SlotSelector.slot_queries` (never `slot_encodings`) |
| correspondence matrix `C^a` | `correspondence`, on `SchemaPrediction` too (never `selection_logits`, never `log_A`) |
| soft assignment `S^a`, selection `S̃^a` | `selection` |
| slot probabilities `w^a` | `slot_weight_logits`, `slot_weights` |
| number of slots `M`, objects `O`, embedding width `d` | `num_slots`, `num_objects`, `object_dim` |
| lifted atom `p(x1, ..., x\|p\|)` | `schema.action.LiftedAtom`, over `slots` (never `GroundAtom`, never `object_index`) |
| `P_add` / `P_del` / `P_pre+` / `P_pre-` | `Channels.positive` / `.negative` on `effects` / `preconditions` |
| `p_pre` | `precondition_satisfaction` |
| τ, the root degree of the relaxed product | `precondition_tau` (the schedule), `tau` (the value at a step) |
| `L_adj`, `L_aux`, weight `α` | `Losses.adjacency`, `Losses.auxiliary`, `aux_loss_weight` |
| PCGrad's norm cap (App. A.2.2) | `pcgrad_norm_cap` |
| `N_min^tr` .. `N_max^val`, per action name | `min_per_action_train` .. `max_per_action_valid` (never `per_label`) |
| derivation of action schemas (Sec. 4.5) | `validation.decoding.derive_schema` |
| soundness / completeness | `precision` / `recall`, `tp` / `fp` / `fn` |

Three deliberate departures. **"Relation" is not always the paper's "predicate"**: a relation is a predicate that became a channel of the adjacency tensor, which `schema.domain.tensor_relations` decides, so `pddl/` and `transpiler.py` say `predicate_*` where they mean the PDDL declaration and everything tensor-side says `relation_*`. And **an argument named for a tensor axis keeps the axis's name** (`y_action`, `edge_index`), which is PyG's convention, not this repository's. And **the model whose effects come from an MLP is not called a baseline**: it is one configuration of the same model (`state_dependent_effects=True`), differing in where the effects come from, so it is "MLP effects" throughout, in `models/effects.StateDependentEffects` and in `validation/mlp_effects.MlpEffectsValidator`. The word baseline is left to L1, which is another system's output. The CLI keys are unaffected: `--experiment-type mlp`, `--validator mlp` and `configs/experiments/mlp.yaml` name the experiment, not its role.

**An attribute of a PyG `Data` object must not have `index` or `batch` anywhere in its name unless it means what PyG takes those to mean.** `Data.__cat_dim__` and `Data.__inc__` key on the substring: a key containing `index` is concatenated along the last axis and offset by `num_nodes` per graph, and one containing `batch` is offset by its own maximum. That is why the action label on the graph is `y_action` and not the `action_index` it is called everywhere else; named `action_index`, three transitions labelled 0, 1, 2 over a 4-object instance batch to `[0, 5, 10]`, silently, with no error anywhere. The restriction is on `Data` attributes alone: `PddlTransitionDataset.action_indices` and `sample["action_index"]` are plain tensors and keep the clearer name. A `Data` subclass overriding both hooks would lift it, which is more machinery than a name is worth.

Renaming a constructor argument of `DIAS` needs a rule in `models/checkpoints._RENAMED_HPARAMS` and a line in `tests/test_checkpoint_layout.UNVERSIONED_HPARAM_NAMES`: Lightning drops a hyper-parameter it does not recognise rather than raising, so without one an archived run silently falls back to a default. A datamodule argument does not, since nothing feeds stored datamodule hyper-parameters back to the constructor; only specific keys are read out of them.

## Editing Rules For This Repository

- Prefer minimal, behavior-preserving changes.
- Preserve the distinction between single-domain training, per-checkpoint validation, and full sweep orchestration.
- Do not silently change experiment semantics stored in YAML manifests or config defaults without updating the relevant documentation and runners.
- Treat the `pddl/<domain>/` folder layout as the source of truth for per-domain paths, reached through `experiments/pipeline.py`'s helpers, and `pddl/<domain>/config.yaml` as the source of truth for per-domain sampling/model overrides.
- Keep standardized filenames in `pddl/` intact unless there is an explicit migration: they are load-bearing now that nothing lists them. A domain folder missing one of them fails `tests/test_pipeline.py`.
- When changing path conventions, update code, configs, docs, and validation scripts in the same task.
- When changing checkpoint naming, W&B directory layout, or logger config, verify all validation entry points still resolve checkpoints correctly.
- When changing datamodule arguments, check both CLI config compatibility and checkpoint reload compatibility.
- Preserve compatibility with older checkpoints where practical; this repository already contains legacy-hparam filtering in validation code for that reason.

- `--no-wandb` covers *both* steps on *both* backends: it drops the training logger too, which it previously did not. Without a logger the run directory comes from `trainer.default_root_dir`, so `launch.run_directory_args` (mirrored in `experiments/slurm/train.sh`) names `<logs>/dias/<run_id>` explicitly; otherwise checkpoints land in `./checkpoints` and validation cannot find them.

## Documentation Rules

- The public documentation is `README.md` (what DIAS is, install, quickstart, the domains, a short reproduction section) and `experiments/README.md` (the full sweep / ablation / threshold recipes). `experiments/scaling/README.md` covers the scaling study. Public docs must not point at `local/`, which is gitignored.
- When documenting commands, prefer the commands that match the current workspace state, especially `configs/main.yaml` and `experiments/configs/validation.yaml`.
- If you encounter stale references to `configs/main.yaml`, either update them or clearly mark them as stale.
- Keep explanations aligned with the paper: symbolic states are fully observed in this repository pipeline, while action supervision varies by experiment.
- Prefer precise planning terminology: predicates, lifted action schemas, preconditions, add effects, delete effects, successor states, STRIPS, and STRIPS+.
- **Prose is not hard-wrapped, and it has no dashes.** One paragraph is one line, in markdown, in docstrings and in `#` comments (Python, YAML, TOML, shell) alike: editors wrap for themselves, and a manual line break inside a sentence only breaks that wrapping. An example command is one line too, however long, rather than a backslash continuation per flag, and so is a long string literal in Python: one literal on one line, not implicit concatenation split across several. Line structure is reserved for things that have one anyway: list items, tables, code blocks, aligned definition lists, and the real multi-line commands in `experiments/slurm/*.sh`.
- Where a dash would have gone, use a colon, a semicolon, a comma or parentheses. This is about the punctuation, not the character: `--` is the same device as an em-dash and is no more welcome.
